**Behaviour change — a request that used to succeed can now answer 400:** an `include` or `sort` query parameter on an endpoint whose `query` schema does not declare it is now rejected with **400 Bad Request** instead of being ignored, as JSON:API 1.1 requires. For `include`, §Inclusion of Related Resources: "If an endpoint does not support the `include` parameter, it **MUST** respond with `400 Bad Request` to any requests that include it." For `sort` on an endpoint that responds with a resource collection, §Sorting: "If the server does not support sorting as specified in the query parameter `sort`, it **MUST** return `400 Bad Request`" (that section "applies to any endpoint that responds with a resource collection as primary data"). For `sort` on any other endpoint, such as a single-resource `GET`, the general rule of §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." For example `GET /articles/1?include=author` on `Endpoint.get(Article)` declared without `include`, `GET /articles/1?sort=title` on any `Endpoint.get`, `GET /articles?sort=title` on an `Endpoint.list` without `sort`, or either parameter on a `DELETE`. Any value is rejected, an empty `?include=` included, as is a bracketed member such as `include[x]`. JSON:API defines only the bare `include` and `sort`, so a bracketed one — `?include[]=author`, `?include[x]=author`, `?sort[title]=1`, `?sort[x][y]=1` — is rejected under the general rule on an endpoint that does declare the bare parameter too, where the query schema used to drop it (#329); a hand-built `query` schema that declares such a name itself (a `"sort[x]"` property) supports that very name. A client that sends one of these and relied on it being ignored must stop sending it.

The 400 carries one error object per offending parameter, naming it in `source.parameter` (`code: "bad_request"`), with a detail saying the endpoint does not support the parameter. The `SchemaErrors` middleware every `Endpoint` constructor attaches answers it before the endpoint decodes anything, under `Middleware.layer`, `Middleware.layerWith`, `Middleware.layerHostNegotiated` and `Middleware.SchemaErrorsLive` alike, and `Middleware.checkQueryParameters` applies the same rule: it rejects `include` and `sort` unless `declared` lists them, and a bracketed `include[…]` / `sort[…]` unless `declared` lists that very name. An endpoint that declares the family with at least one legal value keeps answering as before; one whose vocabulary is empty is covered by a separate entry (#282). `allowedQueryParameters` cannot admit `include`, `sort` or a bracketed name of either: listing one throws `Middleware.InvalidAllowedQueryParameter`, as the entry on reserved query parameters describes. A separate entry extends this 400 to `fields`, `page` and `filter`.
