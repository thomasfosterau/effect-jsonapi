**`Resource.ResolveIncludePath` now distributes over a union of resource definitions and walks each member's includable relationships only, so it no longer crosses one member's `paginated` relationship on a path that is legal for another member (#347).** `Resource.IncludedFor`, `Resource.FamilyIncluded` and `Client.narrowIncluded` follow. With `Post.author = Relationship.one(() => Person)` and `Draft.author = Relationship.paginated(() => Revision)`, `Resource.FamilyIncluded<typeof Entries, ["author"]>` is `typeof Person` where it was `typeof Person | typeof Revision`, and the same holds at any later hop. A `paginated` relationship's target never appears in `included`, so the dropped types are ones no compliant response carries. These are now the same types the endpoint documents and `fields: true` derive.

The change is type-level only. It is a minor release because code that compiled against the released types can stop compiling, in these ways:

- **A path segment that only some members declare now reaches the targets of the members that declare it.** Before, it reached nothing for the whole union, so `Resource.FamilyIncluded<typeof Entries, ["author", "editor"]>` left out `editor`'s target, which the server does send. The narrowed union grows: an exhaustive `switch` on a narrowed `included[].type` (a `default` that assigns to `never`) no longer compiles until it handles the added type. This and the wide dotted path below are the breaks in code that was sound before.
- **A path naming another member's `paginated` relationship no longer reaches its target**, as above. A `switch` on a narrowed `included[].type` with a `case` for a type that can no longer occur, such as `"revisions"`, is now a compile error (TS2678). Delete that `case`.
- **On a single resource, a path naming a `paginated` relationship now resolves to `never`**, for every direct user of `Resource.ResolveIncludePath`, `Resource.IncludedFor` and `Resource.FamilyIncluded`, not only through `Client.narrowIncluded` (whose `include` argument already rejected such a path). `Resource.IncludedFor<typeof Draft, ["author"]>` was `typeof Revision` and is now `never`. Such a path is never a legal `include`, so no compliant response carries what it named.
- **A wide dotted path now reaches the includable targets at every hop.** ``Resource.ResolveIncludePath<R, `${string}.${string}`>`` was `R`'s direct targets (a `paginated` one's included) and is now `R`'s includable direct targets and their includable direct targets: on a resource with `author` (to-one `people`), `remarks` (to-many `remarks`, which has a to-one `tags`) and a `paginated` `history` (`revisions`), it was `people | remarks | revisions` and is `people | remarks | tags`. An `any` path resolves the same way. The second-hop targets are reachable, so the union is now correct, but an exhaustive `switch` over it needs a `case` for each added type, and a `case` for a dropped `paginated` target is a compile error (TS2678). The same holds for an endpoint whose `include` allow-list `paths` is typed ``ReadonlyArray<`${string}.${string}`>``: its `included` union and `Query.FieldsetResources` gain the second-hop targets.

A `string` path keeps its meaning, minus `paginated` targets: `Resource.ResolveIncludePath<R, string>` and `Resource.IncludedFor<R, ReadonlyArray<string>>` are `R`'s includable direct targets. A pattern segment such as `` `auth${string}` `` reaches the includable targets of the keys it matches, as it did before for a non-`paginated` key.
