A 400 for a value rejected in a request body, header or path parameter now names, in `source`, the key the request sent when the schema renames it on the wire with `Schema.encodeKeys`. A body member `count` that `Schema.encodeKeys({ count: "itemCount" })` sends as `itemCount` is now reported as `source.pointer: "/itemCount"`, at any depth (`/data/itemCount` for a renamed struct under `data`); a header `trace` sent as `x-trace` as `source.header: "x-trace"`; and a path parameter `id` sent as `itemId` as `source.parameter: "itemId"`. Before, `source` named the decoded key, which the request does not carry (#316). The same holds when a check on the whole renamed struct (`Schema.makeFilter` returning `{ path: ["count"], issue }`) rejects the member. This is the counterpart of #305's fix for query parameters, uses the same mapping and has the same limits, and covers the `SchemaErrors` middleware and `Middleware.schemaErrorDocument` called with `"Payload"`, `"Body"`, `"Headers"` or `"Params"`. A schema that renames nothing answers exactly as before. To read a renamed struct's wire names, its transformation's decode runs on probe values once per schema, as #305 does for queries, so a decode with side effects has them run then.
