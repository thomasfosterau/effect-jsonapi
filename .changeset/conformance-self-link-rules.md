`Conformance` gains four spec-tier rules on the link crawl (#309): two MUSTs and, as `related-dereferences` and `related-matches-linkage` split the `related` link, a SHOULD beside each. All four use the crawl the other link rules use: same-origin only, `GET` only, 200 requests per rule, and a server error, a `429`, a `408` or a lost response leaves the link not decided. Each SHOULD leaves a link its MUST fails (one that does not parse, answers a non-2xx or answers something the MUST rejects) not decided, naming that rule, so one broken link is never failed twice. `skip: ["spec/links/"]` leaves all four out with the rest.

- `spec/links/relationship-self-dereferences` (MUST) follows every relationship's own `links.self` (JSON:API 1.1 §Fetching Relationships: "A server **MUST** support fetching relationship data for every relationship URL provided as a `self` link …", and "The primary data in the response document **MUST** match the appropriate value for resource linkage"). The answer must be resource linkage: `null`, a resource identifier object or an array of them. An identifier object carries a string `type` and a string `id`, and nothing but those, `lid` and `meta`, so full resource objects fail, and so does an identifier naming its resource by `lid` alone. An @-member and an extension member (`ns:member`) are not counted against an identifier. The cardinality must match the relationship's linkage: `null` or one identifier for to-one, an array for to-many. A links-only relationship shows no cardinality, so it is held only to answering linkage (#390). A non-2xx answer is a finding expecting "resource linkage" either way.
- `spec/links/relationship-self-matches-linkage` (SHOULD, §Relationships: the relationship link "returns the linkage for the related resources as its primary data", with no keyword) follows the `self` of every relationship that carries linkage. The answer must name the same identifiers. As in `spec/links/related-matches-linkage`, the check relaxes to a subset when either side carries `next`, and nothing is decided when both do.
- `spec/links/top-level-self-dereferences` (MUST) follows every document's top-level `links.self` (§Fetching Resources), relationship endpoints' documents included. The answer must be resource data: a resource object, an array of them or `null`.
- `spec/links/top-level-self-matches-document` (SHOULD, §Document Top Level: `self` is "the link that generated the current response document", with no keyword) follows the same links. The answer must be a document of the same kind. A single resource must answer the same `type` and `id`, and `null` must answer `null`. A collection must answer a collection. It must hold the same resources, in any order, only when neither document carries `next` or `prev`, because a page can differ from the document it is compared with.

`Conformance.gaps` no longer lists "Relationship and top-level `self` links".
