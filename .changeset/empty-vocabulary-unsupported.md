**Behaviour change: an `include` or `sort` family declared with an empty vocabulary now counts as unsupported, so a request that used to succeed can now answer 400.** This covers `include: { paths: [] }`, `include: true` on a resource with no relationships, and `sort: true` on a resource with no attributes. The `SchemaErrors` middleware now answers any `?include=` or `?sort=` on such an endpoint exactly as it answers one on an endpoint that never declared the family: a 400 naming the parameter in `source.parameter`, with the detail saying the endpoint does not support it. That includes an empty value (`?include=`, `?sort=`), which used to answer 200, and a bracketed member such as `include[x]`, which used to be ignored. A non-empty value used to answer 400 with the detail `Expected never` and `meta.includablePaths: []` / `meta.sortableFields: []`. It now gets that same unsupported-parameter 400, without the `meta` (#282). Because the middleware answers it before content negotiation, such a request that also carries an unacceptable `Accept` or an unsupported `Content-Type` now answers this 400 where it used to answer 406 or 415, as on an endpoint that never declared the family.

Only the codec the `include` / `sort` query parameter itself decodes through counts, read through a union and through `Schema.suspend`: the property the query's encoding sends under that wire name, whatever its decoded name. With `Schema.encodeKeys({ paths: "include", order: "sort" })`, `paths` decides `include` and `order` decides `sort`; a decoded `include` sent as `inc` decides nothing about `include`; a transformation between two structs that renames nothing pairs each name with itself, whatever order either struct lists them in. The property is found by running the query's encoding on probe values, once per query schema: on every wire parameter at once and on each alone. A wire parameter is paired with a decoded property only when its value lands there, and only there, both alone and among the rest, and no other wire parameter alone puts a value there; a decoded property that either of two wire parameters can fill (`include ?? inc`) is paired with neither. Where the probes cannot show which property it is (a chain of more than one transformation, one that fails or goes asynchronous on a probe, a `Middleware`), the property of that name decides, or failing one, every property whose name the wire does not declare. A hand-built query whose `include` parameter decodes through `Query.IncludeList`, or whose `sort` parameter decodes through a custom codec, publishes no vocabulary and keeps the family supported, and so does a union in which any member's vocabulary is non-empty. A vocabulary under another parameter, such as a second `Query.Include` the query declares as `other`, never decides it.

Where such a value still reaches the codec, its rejection now says why: a direct decode with `Query.Include`, `Query.Sort` or `Query.schema`, without the middleware. The detail is `This endpoint supports no include paths.` or `This endpoint supports no sortable fields.` in place of `Expected never`.
