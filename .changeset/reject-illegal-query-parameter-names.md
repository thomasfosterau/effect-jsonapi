**Behaviour change:** a query parameter whose family base name is not a legal JSON:API member name (`?foo!=1`, `?page.limit=1`, `?[x]=1`, `?__proto__=1`), or that names an extension's parameter (`?ext:param=1` — a namespace, a colon and a-z), is now answered with **400 Bad Request** naming it in `source.parameter` instead of being ignored, unless the endpoint's `query` schema declares it or `allowedQueryParameters` lists it (#263). JSON:API 1.1 §Query Parameters requires the 400 for a parameter that "does not follow the naming conventions"; none of this package's extensions defines a query parameter. Bracketed families (`filter[x]`, `page[limit]`, `fields[articles]`) are judged by their base name and are unaffected, as are implementation-specific names — legal member names carrying a character outside a-z, such as `?fooBar=1`, `?x-trace=1` or `?utm_source=`.

`allowedQueryParameters` now defaults to `["_"]`, so jQuery's cache-buster (`?_=<timestamp>`, from `$.ajax({ cache: false })`) keeps working. A list you pass replaces the default: a host that passes `["lang"]` must list `"_"` too to keep admitting it (`["_", "lang"]`), and `[]` answers `?_=` 400 as well. An entry may now also be an extension's parameter (`"ext:param"`) or another name that is not a legal member name (`"foo!"`); `Middleware.InvalidAllowedQueryParameter` is still thrown for an entry the check would never reject — now including a legal member name with a character outside a-z (`x-trace`), a percent-encoded spelling (`page%5Bsize%5D`) and an entry with an empty base name (`[x]`) — while an entry with surrounding whitespace (` lang`), which used to be refused, is now an illegal name the entry admits.
