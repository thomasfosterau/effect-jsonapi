A 400 for a rejected query value now names, in `source.parameter`, the parameter the request sent when the query schema renames it on the wire. A property `paths` that `Schema.encodeKeys({ paths: "include" })` sends as `include` is now reported as `include`, and the `limit` of `Query.bracketPageKeys`, `Query.bracketKeys` or `Query.flatList` as `page[limit]`. Before, `source.parameter` named the decoded property (`paths`, `limit`), which is not a parameter the request carries (#305). The same holds when a check on the whole renamed struct (`Schema.makeFilter` returning `{ path: ["limit"], issue }`) rejects the property. This covers the `SchemaErrors` middleware and `Middleware.schemaErrorDocument` called with `"Query"` on a host's own decode. A value rejected before the rename was already reported under its wire name and is unchanged, and so is every query that renames nothing. A property the query's own transformation does not show to come from one parameter alone, such as one that either of two parameters fills on its own (`include ?? inc`), keeps its decoded name, as before. The transformation is read on probe values, so a decode that chooses a parameter by its value, or fills a property only from a combination of parameters, can still be misread (as the decoded-name fallback misreads it today).
