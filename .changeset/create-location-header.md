A `201` from `Endpoint.create` (and so from `Endpoint.resource` / `Group.resource`) now carries a `Location` header, as JSON:API v1.1 §Creating Resources → 201 Created recommends. The new `Middleware.CreatedLocation` middleware, which `Endpoint.create` attaches, copies it verbatim from the encoded document: the created resource's `data.links.self`, or, when that is missing, the document's top-level `links.self` (a link object contributes its `href`). So when the resource carries `links.self`, the two match by construction, as the spec requires. With neither link the header is omitted. Only a `201` is touched. A create answering another `status` is left alone, and so is a response that already carries `Location`. A body that is not a JSON document, or is not settled bytes, passes through unchanged and never fails the request. The middleware sits inside `Idempotency.Middleware`, so a recorded `201` keeps its `Location` and a replay returns it. Handlers need no change. Give the created resource its own `links.self` (`Handlers.data({ ...resource, links: { self } }, { self })`) for the header to name it.

`Middleware.layer`, `Middleware.layerWith` and `Middleware.layerHostNegotiated` provide the new `Middleware.CreatedLocationLive`, so an api built on them needs no change. **An api that composes its own middleware set** (for example `Middleware.ContentNegotiationPassthrough` beside `Middleware.schemaErrorsLayer(…)`) and has a create endpoint no longer type-checks until it adds `Middleware.CreatedLocationLive` to that set. The header is not declared on the endpoint, so the typed client does not surface it.
