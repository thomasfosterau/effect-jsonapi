`Conformance` gains `spec/pagination/links-enumerate-collection`, a spec-tier MUST that walks a collection's pagination links (JSON:API 1.1 §Pagination: "The following keys **MUST** be used for pagination links: `first`: the first page of data, `last`: the last page of data, `prev`: the previous page of data, `next`: the next page of data", and "Keys **MUST** either be omitted or have a `null` value to indicate that a particular link is unavailable"). For every list or related endpoint that declares `page[limit]` or `page[size]` and whose URL resolves, the kit fetches the collection with no page parameters (walking the server's own pages when it pages by default), then follows `next` from the first page at a page size that forces a different partition. It fails on a resource listed on two pages, one never reached or not in the collection, `prev` on the first page, a `next` that leads back to a page already visited, to a page listing no resources, to something that is not a page or is not a link, and on `first` or `last` answering different resources from the first or last page. It works off the links alone, so offset, page-number and cursor pagination are checked alike.

The walk is bounded — 20 pages per walk, 200 requests per run of the rule, and a cyclic or non-advancing `next` ends it — and a walk that runs out of budget, or whose `next` leads to another origin (never followed), is reported `Skipped`, never as a pass. Without `sort`, JSON:API requires no stable order (§Sorting: the server "MAY apply default sorting rules"), so when a repeat or gap could come from the order shifting, the kit asks for the first pages again and, if their order changed, reports the collection not decided rather than failing it. The rule skips, saying why, when no endpoint declares a page size, a collection holds fewer than two resources, or the server answers everything on one page. A run now makes about six to ten more requests per paginated collection.

`Conformance.gaps` no longer lists "Pagination link correctness".
