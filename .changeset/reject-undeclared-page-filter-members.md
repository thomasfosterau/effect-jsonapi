The `SchemaErrors` middleware (`Middleware.layer`, `Middleware.layerWith`, `Middleware.schemaErrorsLayer`, `Middleware.SchemaErrorsLive`) now answers a `page` or `filter` member the endpoint does not declare with a 400, under the spec's general rule (JSON:API 1.1 §Query Parameters), where the query schema used to drop it silently. On an endpoint with an explicit filter map (`filter: { status: … }`) or declared page keys (`Query.Page.Offset`, `Query.Page.Number`, `Query.Page.Cursor`, custom keys, a `Query.bracketPageKeys` struct), `?filter[stauts]=open`, `?page[sise]=10`, a deeper `filter[status][eq]` and a bare `filter` or `page` are each rejected with `source.parameter` naming the parameter as the request spelt it and a `detail` listing the members the endpoint does declare, instead of returning an unfiltered or unpaginated collection. A member counts by its wire name (`Schema.encodeKeys({ state: "filter[status]" })` declares `filter[status]`). `filter: true` is unchanged, since its grammar declares every `filter[…]` and rejects malformed members itself, and so is a hand-built open record of a family (`Schema.TemplateLiteral(["filter[", …])`). `Middleware.checkQueryParameters` applies the same rule: a declared `page[limit]` no longer admits the whole `page` family, so a host that listed one member to admit the family must now list each member, or a `page[` prefix.
