`Conformance`'s `spec/document/full-linkage` rule reports an orphaned `included` resource whose `type` or `id` is not a string as a finding. It rendered the pair with `String`, which throws on valid JSON such as `{"type":{"toString":1},"id":"2"}`, so the rule came out `Errored` instead of `Failed`. A string `type` or `id` still reads as itself; any other value now reads through `Formatter.format` (`{"toString":1}:2`). `spec/document/no-duplicate-resources` had the same fault: two copies of `{"type":"people","id":{"toString":1},"lid":"9"}` in `included` made it `Errored`; it now reports them as a finding. Both rules name a resource by the member the kit compares it on — its `id` when that is a string, else its `lid` — so a duplicate identified by `lid` reads `people:9` (it read `people:undefined`), and `{"type":"people","id":7,"lid":"8"}` reads `people:8`, not by the `id` the comparison ignored.

`Conformance.format` keeps a value that spans lines inside its entry: a `WRITES` entry whose `cleanup-failed` detail has more than one line — an `Error("a\nb")` from `cleanup` — hangs the later lines under the entry instead of starting them at the margin; a finding whose detail has more than one line marks only the first with `·`; and an `expected:` or `observed:` value that spans lines — a server `type` of `"a\nb"`, say — hangs its later lines under the label instead of starting them at the label's column.
