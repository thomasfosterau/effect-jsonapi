**Behaviour change:** a query parameter whose family base name is made only of the letters a-z, and that neither the JSON:API specification defines (`include`, `fields`, `sort`, `page` and `filter`, each a 400 on an endpoint that does not declare it, as the separate entries on unsupported `include` / `sort` and `fields` / `page` / `filter` describe) nor the endpoint's `query` schema declares, is now answered with **400 Bad Request** instead of being ignored. JSON:API 1.1 §Query Parameters reserves those names for the specification and requires the 400. A request such as `GET /articles/1?unknown=1` or `?foo[bar]=1` that used to succeed now fails, with one error object per offending parameter naming it in `source.parameter` (`code: "bad_request"`, the shape every other query 400 has). Implementation-specific names — any carrying a character outside a-z, such as `?fooBar=1`, `?x-trace=1` or `?utm_source=…` — are still ignored.

Lowercase parameters a client or host is likely to send that now answer 400 unless the endpoint's `query` schema declares them or the host allows them: search and locale parameters (`?q=`, `?search=`, `?lang=`, `?locale=`), non-JSON:API paging (`?limit=`, `?offset=`), formats and callbacks (`?format=`, `?callback=`), tokens and referrers (`?token=`, `?ref=`), cache-busters (`?t=`, `?v=`) and click identifiers appended by ad and analytics tools (`?fbclid=`, `?gclid=`). Anything carrying a capital, digit, `-`, `_` or `:` (`?utm_source=`, `?_=`, `?x-trace=`) is unaffected.

The check runs in the `SchemaErrors` middleware every `Endpoint` constructor attaches, so it covers every endpoint, including those that declare no query schema, under `Middleware.layer`, `Middleware.layerWith`, `Middleware.layerHostNegotiated` and `Middleware.SchemaErrorsLive` alike. A host whose URL space carries its own lowercase parameters through to the api can list them by family base name — `Middleware.layerWith({ allowedQueryParameters: ["lang"] })`, or the new `Middleware.schemaErrorsLayer({ allowedQueryParameters })` beside `Middleware.ContentNegotiationPassthrough` — or rename them. Each entry must be such a base name: one that is not (`lang[region]`, `Lang`, ` lang`, `""`) throws the new `Middleware.InvalidAllowedQueryParameter` when the layer is built, and from `checkQueryParameters`, instead of admitting nothing. So does an entry naming one of the specification's families (`include`, `fields`, `sort`, `page`, `filter`), or a bracketed member of one (`page[size]`, `filter[status]`), which the allow-list cannot admit: its message says to remove the entry, since an endpoint supports such a parameter by declaring it in its `query` schema. `Middleware.checkQueryParameters(names, { declared, allowedQueryParameters })` is the same rule standalone, for a framework hook that decodes requests itself.
