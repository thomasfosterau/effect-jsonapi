**Behaviour change:** a query parameter whose family base name is made only of the letters a-z, and that neither the JSON:API specification defines (`include`, `fields`, `sort`, `page`, `filter`) nor the endpoint's `query` schema declares, is now answered with **400 Bad Request** instead of being ignored. JSON:API 1.1 §Query Parameters reserves those names for the specification and requires the 400. A request such as `GET /articles/1?unknown=1` or `?foo[bar]=1` that used to succeed now fails, with one error object per offending parameter naming it in `source.parameter` (`code: "bad_request"`, the shape every other query 400 has). Implementation-specific names — any carrying a character outside a-z, such as `?fooBar=1`, `?x-trace=1` or `?utm_source=…` — are still ignored.

The check runs in the `SchemaErrors` middleware every `Endpoint` constructor attaches, so it covers every endpoint, including those that declare no query schema, under `Middleware.layer`, `Middleware.layerWith`, `Middleware.layerHostNegotiated` and `Middleware.SchemaErrorsLive` alike. A host whose URL space carries its own lowercase parameters through to the api can list them by family base name — `Middleware.layerWith({ allowedQueryParameters: ["lang"] })`, or the new `Middleware.schemaErrorsLayer({ allowedQueryParameters })` beside `Middleware.ContentNegotiationPassthrough` — or rename them. `Middleware.checkQueryParameters(names, { declared, allowedQueryParameters })` is the same rule standalone, for a framework hook that decodes requests itself.
