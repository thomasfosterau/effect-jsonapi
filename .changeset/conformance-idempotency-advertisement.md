`Conformance` gains `profile/idempotency/advertises-profile-uri`, the first rule for the Idempotency-Key profile, a SHOULD citing `docs/idempotency.md` §1. Given a `writes` fixture and `mutating: true`, the kit sends one create to each create endpoint whose headers declare the header (`idempotency: true` or `"required"`), and one create plus one update (the `update` fixture) of what it made to each such update endpoint — at most one create and one update per type. Each 2xx must name `Idempotency.PROFILE_URI` in the top-level `jsonapi.profile` member or in the media type's `profile` parameter. Either place passes, and a media type naming it passes even with no body. A package-built endpoint passes when its handler answers with `jsonapi: Idempotency.jsonapi`. Without `mutating: true`, without a fixture, or with no endpoint declaring the header, the rule skips and says which. A write the server does not accept, or a 2xx with no document whose media type does not name the profile, decides nothing. Delete endpoints and the atomic operations endpoint are not checked.

Every write rule that creates, updates or deletes through a resource endpoint now sends a fresh `Idempotency-Key` to an endpoint declared `idempotency: "required"`, which would otherwise refuse the write with a 400 and leave the rule undecided. An endpoint where the key is optional gets none.

The `The Idempotency-Key profile` coverage gap no longer calls this rule non-mutating and unwritten. It is narrowed to delete and atomic writes and to what a retried write does (replay, fingerprint mismatch, in-flight, key scope), which still needs byte-for-byte replay (#162, #165). The `Tier` and module descriptions now name the Idempotency-Key profile as part of the `profile` tier.
