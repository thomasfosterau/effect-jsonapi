`fields: true` now declares a sparse fieldset for every type an include path the endpoint legalises reaches, not only for the resource and its direct relationship targets (#311). `include: true` legalises paths two relationships deep, so an endpoint with both could return, in `included`, a type it declared no `fields[TYPE]` for, and with this release's 400 for an undeclared `fields[TYPE]` a client could include such a type but never trim it: `GET /articles/1?include=comments.author&fields[people]=name` answered 400 naming `fields[people]` when `people` is a target of `comments`, not of `articles`. It now decodes to `{ include: ["comments.author"], fields: { people: ["name"] } }`. JSON:API 1.1 §Sparse Fieldsets: "A client **MAY** request that an endpoint return only specific [fields] in the response on a per-type basis by including a `fields[TYPE]` query parameter."

The declared set is the resource, its direct relationship targets (kept whatever `include` says, as before) and every resource on the way down each legal include path, its leaf included: two hops under `include: true`, the `depth` a `Query.IncludeOptions` names, or exactly the `paths` of an allow-list or a declared `Include.Surface` (`comments.author.employer` declares `comments`, `people` and `companies`). With `include` off nothing changes. A type no legal path reaches — the target of an included resource's `paginated` relationship (never an include path), or one a hop past the deepest path — is still a 400, and a reached type with no attribute still gets the empty-vocabulary 400. The decoded `fields` struct, the flat `fields[TYPE]` keys and `Query.FieldsetResources` follow the same set; `Query.FieldsetResources` takes the `include` option as a new, optional second type parameter (`Query.FieldsetResources<typeof Article, true>`), and without it is unchanged.

This only widens what a query accepts: no request that decoded before is rejected now, and a decoded `fields` gains optional keys only.
