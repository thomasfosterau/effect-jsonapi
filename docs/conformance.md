# Conformance kit

Design note for `Conformance` — the executable specification a server is driven through to prove it implements JSON:API v1.1, and this package's profile. Tracks [#120](https://github.com/thomasfosterau/effect-jsonapi/issues/120) (epic [#115](https://github.com/thomasfosterau/effect-jsonapi/issues/115)).

**Status:** v1 implemented, plus the write fixture ([#162](https://github.com/thomasfosterau/effect-jsonapi/issues/162)). 57 rules (51 `spec`, 6 `profile`), six declared coverage gaps; `Conformance.rules` and `Conformance.gaps` are the live lists.

## 0. Why it exists

The package's premise is that compliance is _"a property of the construction, not of developer discipline"_. That holds for what the endpoint constructors generate — the media type, the status codes, the negotiation rules. It says nothing about a server once a handler has an opinion, and until now there was no way for anyone to check. `HttpApiTest` exists and the package's own tests use it, but a consumer had nothing to run.

The kit is the other half: an oracle that fails **naming the broken rule and citing its section**, not printing an assertion diff.

> `spec/content-negotiation/accept-weight-is-not-a-parameter` — MUST NOT, Content Negotiation (with RFC 9110 §12.4.2) A `q` weight is an Accept-header parameter, not a media type parameter …

versus `expected 200, got 406`.

## 1. What is under test

**A transport, discovered from an `HttpApi` value.**

Two things are deliberately separated:

- **Discovery is static.** `Conformance.verify` walks `api.groups[*].endpoints[*]` and reads each endpoint's method, path, path parameters, flat wire query keys (`include`, `sort`, `fields[articles]`, `page[limit]`, and whether `filter[…]` is an index signature — i.e. the grammar — or named keys — i.e. the escape hatch) and its declared response media type. The query keys are read by the same walk `Middleware.SchemaErrors` checks requests against, so a hand-built query that is a union declares what any member declares and a suspended one what its target declares; a query that could accept a name the walk cannot enumerate — a record keyed by any string, say — is recorded as such, as the middleware stands aside for it. From the method and the path's segment shape it assigns a **role**: `collection`, `resource`, `create`, `update`, `delete`, `related`, `relationship`, `relationshipWrite`, `operations`. Nothing is requested during discovery, so the report can name both the endpoints it probed and the ones it could not build a URL for.
- **Observation is wire-level.** Every rule is decided by a real request/response pair.

### 1.1 Why not the typed client

`HttpApiTest.groups` returns an `HttpApiClient`, which is the wrong instrument here for two reasons:

1. **It hides what has to be checked.** Conformance is a wire property — the raw status code, the media type's _parameters_, the unparsed body, whether `included` carries a duplicate. The typed client decodes all of that away.
2. **It cannot express the probes.** Half the rules send deliberately malformed requests: a `Content-Type` with a `charset` parameter, an `Accept` whose every JSON:API instance is parameterised, `?fields[articles]=` naming a field that is not there, `?unknown=1`, a repeated `filter[…]` key. A typed client refuses to construct them, which is exactly its job and exactly why it is not the seam.

So the kit builds an in-memory `HttpClient` over the real router — the same `HttpRouter.toHttpEffect` + `HttpClient.make` technique `HttpApiTest` uses, stopping one step earlier — and drives raw requests through it.

### 1.2 In-process _and_ over the wire

This is not an either/or, and it should not be two kits.

|  | `Conformance.verify` | `Conformance.verifyWith` |
| --- | --- | --- |
| Transport | in-memory over the real router | any `HttpClient` you pass |
| Binds a port | no | n/a (whatever you point it at) |
| Handlers | from the ambient context, as `HttpApiTest` takes them | the deployed server's |
| Rules | **identical** | **identical** |

In-process is the default because it is deterministic, fast (~100–200 requests in well under a second) and needs no fixture beyond sample ids. It still exercises request decoding, routing, middleware, the handler and response encoding — the whole pipeline the rules care about. A request no route serves — which a link the server emitted can lead to — is answered as a deployed server answers it (`HttpServerError.causeResponse` on the router's `RouteNotFound`: an empty 404), not turned into a defect that would make the rule that sent it `Errored` ([#168](https://github.com/thomasfosterau/effect-jsonapi/issues/168)). Only `RouteNotFound` is answered so: any other failure of the router, like any defect, still dies, as a transport that throws does, because what a deployed server would answer to it is not known. `verifyWith` takes `FetchHttpClient` and runs the same rules against a deployed server, for the things only a real deployment has: a reverse proxy rewriting `Content-Type`, a CDN, a gateway that normalises headers.

**A redirect is followed only within the base URL's origin** (owner decision on [#168](https://github.com/thomasfosterau/effect-jsonapi/issues/168#issuecomment-6180320627)). The transport itself follows nothing: over the wire the kit provides `FetchHttpClient.RequestInit` with `redirect: "manual"` for its own requests, set over the rest of the `RequestInit` the run's context holds, so a run's own `redirect: "follow"` cannot undo it. The kit then follows a redirect itself, in both transports, after checking where its `Location` leads: only to the base URL's origin — scheme, host and port, so an `http` → `https` redirect on the same host is to another origin — and so, unless the client follows redirects itself (below), no request is ever sent to another origin on a server's say-so. A `301`, `302` or `303` is followed only for a `GET`, since `fetch` would turn any other method into a `GET`; a `307` or `308` re-sends the same method and body. At most five hops are followed for one request, each a request of its own that counts against a rule's request budget, and the final answer is what the rule grades. A `3xx` with no `Location`, or an empty one, answers as itself. A redirect the kit does not follow — to another origin, past the cap or the budget, turning a write into a `GET`, or to a `Location` that does not parse — leaves the request with no answer to read, and so does one a transport followed on its own to another origin or turning the method into a `GET` (below). A rule that sent such a request — a probe, a read endpoint a link rule searches, a link it follows, a page of a pagination walk — drops a finding the request produced, so a probe that was never answered is never reported "not rejected", while a finding on an answer the kit did read still fails the rule. Otherwise the rule is `Skipped`, naming the redirects — the first three by their request and `Location`, the rest counted — and keeping the rule's own note; a rule that skipped on its own keeps its reason, with the redirects named after it. There is never a partial pass on the answers it did read, and no rule opts out, the link rules and the pagination walk included (owner decision on [#333](https://github.com/thomasfosterau/effect-jsonapi/pull/333#issuecomment-6181006987)). `spec/target/reachable` alone decides for itself: a read endpoint that answers with a redirect the kit does not follow is a finding there, telling the caller what to change — point `baseUrl` at the URL that serves; for a chain on the base URL's origin past the hop cap, shorten the chain; for a `Location` that does not parse, fix it on the server; for a redirect the transport followed itself, pass a client that does not. A client that rewrites every request onto another origin (`HttpClient.mapRequest` mapping a `baseUrl` of `http://api.invalid` onto a local port, say) follows nothing, and is read as the server it sends to ([#359](https://github.com/thomasfosterau/effect-jsonapi/issues/359)). The kit runs each request through the client as the client's own `execute` does — its postprocessing, where `HttpClient.followRedirects` follows and `HttpClient.retry` retries, over its preprocessing, where `HttpClient.mapRequest` rewrites — and takes the request the preprocessing last produced as the one the client sent: its origin is where a redirect the transport followed is judged from (below), and a `Location` on that origin, absolute or not, is followed as one on the base URL's, the kit requesting the path it names through the client again. A client that rewrites the path as well (adding a prefix, say) adds it again to the path a followed hop names, exactly as it does to a relative `Location`'s. A preprocessing that fails sends nothing, and is read as a transport error, unless the client's own `retry` recovers from it. Two limits remain. A transport that follows redirects on its own, outside `fetch`'s `RequestInit` (one wrapped in `HttpClient.followRedirects`, say), still sends the request. The kit then refuses to read what the transport ended with — an answer, or a transport error such as a refused connection — when the request behind it is on another origin than the one the client sent, or carries another method (a `301` or `302` turns a `POST`, a `303` any method but `GET`, into a `GET`), and records the request as answered by a redirect it did not follow, naming the URL the transport ended at, so the rule that sent it is held to the same rule as any other redirect the kit does not follow: never a "not rejected", never a partial pass ([#344](https://github.com/thomasfosterau/effect-jsonapi/issues/344)). Only that final URL and method are checked: a chain the transport followed off the origin and back (A → B → A), keeping the method, is read as an answer from A, undetected. And the request has been made either way, so hand `verifyWith` a client that does not follow redirects. And a `RequestInit` given only to the client's own layer (`FetchHttpClient.layer.pipe(Layer.provide(…))`) is replaced for the kit's requests, since the kit's takes precedence there; provide it to the run instead.

### 1.3 The fixture contract

Deliberately the smallest one that works:

```ts
Conformance.verify(api, {
  ids: { articles: "1", people: "9" }, // one known-existing id per resource type
  paths: { "search.search": "/search?filter[q]=x" }, // an explicit URL where the convention can't reach
});
```

`ids` is keyed by resource type, which under the conventional paths is the first literal path segment. A rule that cannot resolve a URL reports **`Skipped`, naming the option it wanted** — never a pass:

```
SKIP  spec/document/top-level-members
      not checked: no sample id for "articles" — pass ids["articles"] or paths["articles.get"]
```

A rule that probed _some_ endpoints but not others passes with a note saying how many it never reached, so partial coverage never reads as full coverage.

### 1.4 The write fixture

`ids` cannot drive a write: the kit cannot synthesise a payload a server will accept (attributes carry domain constraints, required to-one relationships point at resources that must already exist, and a payload rejected with a 422 proves nothing about the 201 rules), and it cannot undo what it created. So the write rules take a second, opt-in contract, keyed by resource type like `ids`:

```ts
Conformance.verify(api, {
  ids: { articles: "1" },
  mutating: true, // the master switch: nothing writes without it
  writes: {
    articles: {
      // a payload the server will accept, in wire form — called once per create
      create: () => ({
        type: "articles",
        attributes: { title: `conformance probe ${++n}`, body: "…" },
        relationships: { author: { data: { type: "people", id: "9" } } },
      }),
      // a PATCH that must succeed against a resource `create` made; the kit adds type and id
      update: () => ({ attributes: { title: `conformance probe ${++n} (updated)` } }),
      // removes a resource the kit created, by the id the server assigned
      cleanup: (id) => Effect.sync(() => store.delete(id)),
    },
  },
});
```

What the kit promises in return:

- **It refuses an id it evidently did not create.** Every write rule creates its own disposable target from `create` — the update rule PATCHes it, the delete rule DELETEs it — and acts on the id the server's create response named only after checking it: the response must name a resource of the type `create` returned (`data.type`, or `atomic:results[0].data.type` for an `add`), under an id that is a URL path segment of its own (not `""`, `.` or `..`, which `encodeURIComponent` leaves alone and URL normalisation turns into the collection or `/`, nor a lone surrogate, which no URL can carry), that is not an `ids` sample, that no successful `GET` earlier in the run returned (as primary data, in `included`, or as a relationship's linkage) unless the kit had already taken it from a create of its own, and that the run does not already hold a resource for that has not been removed (two live resources cannot share an id, so one of the two answers is wrong). Any other id is recorded as `left`, with `detail` naming what was named — "named `people:1`, which the kit did not create … — not touched" — and is never PATCHed, DELETEd or handed to `cleanup`; the rules that would have acted on it skip, saying so. An id the server hands out again once the kit has removed its first holder — a `size + 1` store, a SQLite rowid — is accepted, because refusing it would leave every later resource behind. (Before the fixture, `mutating: true` made the delete rule delete the `ids` sample.) Every rule that creates nothing (the profile tier's included) runs before the first rule that creates, so a create is checked against everything the run reads; the report keeps the suite's order. The read check can refuse falsely: linkage can name a resource since deleted, and a server that reuses ids may hand that id to the kit's create. That fails safe — the resource is recorded as `left` with a `detail` saying why, and the rules that would have acted on it skip.
- **Cleanup runs however the rule ends.** Each target is created inside `Effect.acquireUseRelease`, so `cleanup` runs after the rule that made it whether that rule passed, failed or died. A cleanup that fails or throws is recorded as `cleanup-failed`, not propagated, so one bad cleanup cannot cost the run its report — whatever it fails with: `detail` renders the value as a rule's defect message is, and a value the kit cannot read at all (a revoked `Proxy`, say) as `[unrenderable defect]`.
- **The run is auditable.** `Report.writes` lists every resource the kit created, the rule that created it and what became of it — `deleted` by the kit's own DELETE, `cleaned-up`, `cleanup-failed` with the cause, or `left`. `format` prints them under `WRITES`, with the count still in place.
- **Each sub-key gates only its own rules.** A type with no `create` skips every write rule naming `writes["<type>"].create`, exactly as a missing `ids` entry does; a create-only type omits `update` and skips only the update rule. Never a vacuous pass.
- **A key goes only where one is required.** A write to an endpoint declared `idempotency: "required"` carries a fresh `Idempotency-Key`, so that endpoint does not refuse it with a 400; a key never sent before can only be a first attempt, never a replay. An endpoint where the key is optional gets none, and processes the write normally.
- **A rejected payload is not a verdict.** If the server does not accept `create` (a 4xx, say), the rules it was for report `Skipped` with the status and body — the fixture is wrong or the server is, and the kit cannot tell which.

Four edges of the contract, stated so nobody relies on the opposite:

- **The kit cannot tell a lying server from an honest one.** It refuses only an id that is evidently not what it created — the wrong type, an `ids` sample, one a read returned, a live duplicate, an unsafe path segment. Any other id is trusted, so a server that answers a create with the id of an existing resource the run never saw has the kit update, delete and `cleanup` that resource. Run `writes` only against a server, and data, you can afford to have modified.
- **A non-2xx create is taken to have created nothing.** Nothing is recorded for it and nothing is cleaned up. A server that creates and then answers an error leaves that resource behind, unreported.
- **`cleanup` runs uninterruptibly.** It is the release step of `acquireUseRelease`, so a `cleanup` that never completes hangs the run; give one that talks to a remote store its own timeout.
- **`cleanup` requires no services** (its `R` is `never`): close over, or provide, whatever it needs before handing it to the kit.

**`cleanup` is optional.** Against a target known to be disposable — an in-process store the test throws away — it can be omitted; the kit then leaves what it created in place and says so (`left`, naming `writes["<type>"].cleanup`). Against a server whose state outlives the run, always supply it. This is the less demanding of the two contracts, chosen pending the owner's decision ([§10](#10-open-questions)); the alternative is to require `cleanup` whenever `create` is given.

### 1.5 Against a live server: `skip` and `requestTimeout`

Two options bound what a run costs a server whose state and uptime matter (owner decision on [#302](https://github.com/thomasfosterau/effect-jsonapi/issues/302)): which rules run, and how long the kit waits for an answer.

```ts
Conformance.verifyWith(api, {
  client,
  baseUrl: "https://api.example.com",
  ids: { articles: "1" },
  requestTimeout: "10 seconds", // any Duration.Input; thirty seconds when unset
  skip: ["spec/pagination/links-enumerate-collection", "spec/links/"],
});
```

**`skip` leaves rules out by id prefix — the complement of `only`.** A prefix is matched exactly as `only` matches one, as a plain string prefix of the rule id, so `"spec/links/"` leaves out the seven link rules (the link crawl, §3) and `"spec/pagination/links-enumerate-collection"` the pagination walk, the kit's most expensive rules against a live server. The three selections compose in one order: `tiers` and `only` select, and `skip` removes from what they selected, so a rule both `only` and `skip` name is left out. A rule `skip` leaves out is absent from the report, exactly as one `only` does not select is: the report lists what the run tried, and a `Skipped` outcome means a rule that ran and could not decide (§4.1), not one the caller declined to run. A prefix that matches nothing leaves nothing out, as one in `only` selects nothing. A plain string prefix can reach past the end of a segment: `"spec/status/create-location"` also matches `spec/status/create-location-matches-self`. Making both `only` and `skip` match by segment (an exact id, or ids that continue it with `/`) is [#367](https://github.com/thomasfosterau/effect-jsonapi/issues/367); until then, end a section's prefix with `/`.

**What a run leaves out narrows what the write rules vet a create against.** A create is refused when it names an id a successful `GET` earlier in the run has shown (`Context.observed`, §1.4), a check only as complete as the reads before it — so a read rule `skip` or `only` leaves out, or a read `requestTimeout` cuts short, is a read that check does not see.

**`requestTimeout` bounds each request in time.** A request still unanswered when it runs out is interrupted (over `fetch`, aborted) and reads as a lost response: status `0`, with a transport error naming the timeout (``no response (no answer within 30s, the run's `requestTimeout`)``). Every rule treats it exactly as it treats a refused connection or a reset — `spec/target/reachable` reports it, the pagination walk and the link crawl leave what it cut short not decided — and never as a redirect the kit did not follow, so the [#333](https://github.com/thomasfosterau/effect-jsonapi/pull/333#issuecomment-6181006987) rule that a request a redirect left unanswered skips the rule that sent it does not apply. It bounds one request: the client's whole `execute`, a `retry` the client wraps itself in included (the kit still runs each request through the client exactly as its `execute` does, §1.2), and the reading of the answer's body, so a server that sends its headers and holds the body open is cut short too. Each redirect hop the kit follows is a request of its own, with a timeout of its own and counting against the rule's budget as before, so one probe waits at most six timeouts (the first request and five hops). A request it cuts short was still sent, and still counts against the budget. A create it cuts short is taken to have created nothing, as a non-2xx one is (§1.4): the server may have created it all the same. It does not bound `cleanup`, which is not a request the kit sends (§1.4).

**It defaults to thirty seconds**, for `verify` and `verifyWith` alike (owner decision on [#302](https://github.com/thomasfosterau/effect-jsonapi/issues/302#issuecomment-6186007738)), so a server that holds a response open costs a run at most that per request, and a run that sets nothing is bounded too. Any positive `Duration.Input` overrides it. `requestTimeout: "Infinity"` (or `Duration.infinity`, the same value) turns it off: the kit then waits as long as the transport does, as it did before the option existed, so a server that holds a response open holds the run. `"Infinity"` is the spelling because it is already a `Duration.Input`, so the option keeps one type and needs no second sentinel. A duration that is not positive — zero, a negative one, or `NaN`, which `Duration` reads as zero — would cut every request short before it was answered, so it is a defect in the options, as is one `Duration` cannot read (e.g. `"1e3 seconds"`): the run dies before it sends a request, rather than reporting every rule undecided.

## 2. Two tiers, separately runnable

| Tier | What it is | Authority |
| --- | --- | --- |
| `spec` | JSON:API v1.1 alone | `https://jsonapi.org/format/1.1/` and the atomic extension |
| `profile` | this package's own profiles — the filter grammar and the Idempotency-Key profile — and the conventions it takes a position on where the spec declines to | `docs/filter-grammar.md`, `docs/idempotency.md`, the README |

`tiers: ["spec"]` runs the first without the second, so a consumer can hold themselves to the specification without adopting anything of this library's. A test asserts that no profile rule ever cites `jsonapi.org/format` as its authority.

## 3. What v1 covers

57 rules. Every one carries a stable id, an RFC 2119 level, a section and a URL.

**Content negotiation (§Content Negotiation, §Extensions, §Profiles)** — the response media type and its permitted parameters; 415 on a parameterised request `Content-Type` (probed without `mutating: true`, so it sends the create endpoint — or failing that an update or relationship endpoint — a body `{}` that nothing can apply); 406 when every `Accept` instance is parameterised; an unsupported `ext` URI; an unrecognised `profile` ignored rather than rejected; and the two RFC 9110 §12.4.2 weight rules — a non-zero `q` is not a media type parameter, `q=0` is a refusal. The kit reported the first of those against the shipped middleware before [#101](https://github.com/thomasfosterau/effect-jsonapi/issues/101) was fixed; it now guards the fix against regressing.

**Document structure (§Document Structure, §Compound Documents, §Resource Objects)** — at least one of `data` / `errors` / `meta`; `data` and `errors` never together; `included` only alongside `data`; full linkage, computed transitively from the primary data through included resources' linkage; no duplicate `(type, id)` anywhere in the document; `type` and `id` present and strings; the `jsonapi` object's member types.

The document rules probe **compound** documents, not just bare ones: for each endpoint declaring `include`, the kit reads the includable relationship names off a baseline response (only those carrying inline `data` — a paginated relationship is links-only and including it is a legitimate 400) and re-probes with them. Without that, full linkage and duplicate detection would pass over documents that never carry `included`, which is a pass that proves nothing.

**Error objects (§Errors, §Error Objects)** — the `{ errors: [...] }` shape; member types; `source` discrimination (`pointer` / `parameter` / `header` only, `pointer` a real JSON Pointer); and `status` agreeing with the response status.

**Query parameters (§Sparse Fieldsets, §Inclusion, §Sorting, §Query Parameters)** — sparse fieldsets applying to primary data _and_ to `included` (two rules, because they fail independently — [#112](https://github.com/thomasfosterau/effect-jsonapi/issues/112)); an unidentifiable `include` path is a 400; an unsupported `sort` field is a 400; and an all-lowercase unrecognised query parameter is a 400. Those `include` / `sort` rules probe an endpoint that declares the family; two more probe one that does not ([#278](https://github.com/thomasfosterau/effect-jsonapi/issues/278)), guarding the 400 [#261](https://github.com/thomasfosterau/effect-jsonapi/issues/261) added to the middleware, and seven more send a parameter of a family the specification defines that the endpoint does not declare ([#310](https://github.com/thomasfosterau/effect-jsonapi/issues/310)): a `fields[TYPE]`, `page[…]` or `filter[…]` the endpoint does not support at all (#261), an undeclared member beside the `page` / `filter` members it does declare ([#321](https://github.com/thomasfosterau/effect-jsonapi/issues/321)), and a bracketed `include[]` / `sort[]` beside the bare parameter it supports ([#329](https://github.com/thomasfosterau/effect-jsonapi/issues/329)):

| Rule | Probes | Expects |
| --- | --- | --- |
| `spec/query/include-unsupported-endpoint` | the first read endpoint whose query does not declare `include` and whose baseline response is 2xx, with `?include=` naming a relationship that response carries inline linkage for (else a placeholder) | 400 — §Inclusion of Related Resources: "If an endpoint does not support the `include` parameter, it **MUST** respond with `400 Bad Request` to any requests that include it." |
| `spec/query/sort-unsupported-endpoint` | the first list or related endpoint whose query does not declare `sort` and whose baseline response has a resource collection as primary data, with `?sort=` naming an attribute that response carries (else a placeholder) | 400 — §Sorting: "If the server does not support sorting as specified in the query parameter `sort`, it **MUST** return `400 Bad Request`." The section "applies to any endpoint that responds with a resource collection as primary data", so a single-resource endpoint is not probed: there the 400 rests instead on the general rule in §Implementation-Specific Query Parameters, which this rule does not claim to test. |
| `spec/query/fields-unsupported-endpoint` | the first read endpoint whose baseline response is 2xx and shows a resource type `T` for which the endpoint does not declare `fields[T]` (an endpoint with an open `fields[…]` record is never a candidate), with `?fields[T]=` naming an attribute that response carries (else a placeholder) | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." Ignoring it would also break §Sparse Fieldsets: "If a client requests a restricted set of [fields] for a given resource type, an endpoint **MUST NOT** include additional [fields] in resource objects of that type in its response." |

| `spec/query/filter-unsupported-endpoint` | the first read endpoint whose query declares no `filter` parameter at all (an open `filter[…]` grammar declares the family) and whose baseline response is 2xx, with `?filter[A]=1` for an attribute `A` that response carries (else `filter[x]`) | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." §Filtering only reserves the family, as §Pagination does. |
| `spec/query/page-undeclared-member` | the first read endpoint that declares its `page[…]` members by name, with no open `page[…]` record, and whose baseline response is 2xx, with a member derived from its first declared one so it cannot be another (`page[offset]` → `?page[offset_x]=1`, extended until no declared name admits it) | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." |
| `spec/query/filter-undeclared-member` | as the `page` rule, for `filter[…]` (`filter[status]` → `?filter[status_x]=1`); an endpoint with an open `filter[…]` grammar (`filter: true`), which validates every member itself, is never a candidate | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." |
| `spec/query/include-bracketed` | the first read endpoint that declares the bare `include` and not `include[]`, and whose baseline response is 2xx, with `?include[]=` naming a relationship that response carries inline linkage for (else a placeholder) | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." JSON:API defines only the bare `include`, so a server that reads `include[]` as `include` processes a parameter the specification does not define. |
| `spec/query/sort-bracketed` | as the `include` rule, for `sort` (`?sort[]=` naming an attribute the response carries, else a placeholder) | 400 — §Implementation-Specific Query Parameters: "If a server encounters a query parameter that does not follow the naming conventions above, or the server does not know how to process it as a query parameter from this specification, it **MUST** return `400 Bad Request`." |

Whether an endpoint declares the family is read from discovery (§1: its flat wire query keys), not from a new option. A status other than 400 is a finding. So is a 400 whose error objects carry `source.parameter` naming only other parameters, since that 400 refused something else; a 400 naming no `source.parameter` at all passes with a note saying the status alone decided it, because JSON:API makes `source` optional ("It **SHOULD** include one of the following members or be omitted"); the note says whether the 400 carried error objects without `source.parameter` or no JSON:API error objects at all. A server error (5xx) is a finding too: a server that answers 5xx to a parameter it does not support mishandled it. A rate limit (`429`), a request timeout (`408`) or no response at all (a lost one, or one `requestTimeout` cut short) says nothing of whether the server refuses the parameter, so every refusal rule — the two of #278 and the seven of #310 alike — leaves such a probe not decided, skipped, naming what answered ([#352](https://github.com/thomasfosterau/effect-jsonapi/issues/352)). The link and pagination rules draw that line elsewhere: they decide nothing on a server error either. Each refusal rule sends at most 20 requests, the redirects it follows included — a baseline per endpoint it tries and the one probe — and skips, naming the endpoints it passed over, when that budget runs out before a usable endpoint. The seven read what an endpoint declares by the check `Middleware.SchemaErrors` runs (`declaresName`, over the endpoint's flat wire keys and its open family prefixes), so none sends a name the endpoint declares. Discovery counts a name the endpoint declares with no legal value (a `fields[TYPE]` whose type has no attribute, say) as declared, though the middleware refuses it: the kit then does not probe it, the side on which it can only miss a 400, never demand one the middleware would not give. An endpoint whose query names discovery cannot enumerate (§1) is never probed, since whether it declares the family is unknown. With no endpoint of the right shape the rule skips, saying whether every such endpoint declares the family (or cannot be enumerated), none has a resolvable URL, or none answered a usable baseline — naming what each baseline answered.

**Pagination (§Pagination)** — `spec/pagination/links-enumerate-collection` ([#166](https://github.com/thomasfosterau/effect-jsonapi/issues/166)), the kit's first multi-request, stateful rule. JSON:API 1.1: "The following keys **MUST** be used for pagination links: `first`: the first page of data, `last`: the last page of data, `prev`: the previous page of data, `next`: the next page of data", and "Keys **MUST** either be omitted or have a `null` value to indicate that a particular link is unavailable." The kit is never told the set a server pages over; it derives it, for every list or related endpoint that declares `page[limit]` or `page[size]` and whose URL resolves:

1. **The reference.** `GET` the endpoint with no page parameters. An answer without `next` is the whole collection; one with `next` is the server paging by default, and the reference is the walk of its own pages.
2. **The walk.** Again at a page size that forces a different partition: a third of the collection when it came back whole (about three pages), one fewer than the server's own page size when it pages by default. It sets `page[limit]`, else `page[size]`, on the first request only, and reaches every later page through `next` — so offset, page-number and cursor pagination are checked alike, off the links rather than the strategy.
3. **The verdict.** Each walk: the first page carries no `prev`; no resource is on two pages; `next` never leads back to a page already visited, to a page that lists no resources (the last page carrying `next`), to anything that is not a page of the collection, and is always a link; `first` and `last` on the first page answer the same resources as the first page and the last page the walk reached. Then the walk against the reference: every resource reached, and none the reference does not list.

**Why a `next` to an empty page is a MUST failure.** The base specification defines `next` as "the next page of data" and requires an unavailable link to be omitted or `null`. A page that lists no resources is not a next page of data: the page before it was the last, so its `next` was a link to a page that does not exist, where the spec required none. The [cursor-pagination profile](https://jsonapi.org/profiles/ethanresnick/cursor-pagination/) does allow such a link, but not on a page the walk reads `next` from. Its §Links holds a server to the same answer for any request without `page[before]`: "If a request does not contain the `page[before]` parameter, the server **MUST** determine whether a next page exists, and return `null` as the `next` link if not." The rest — a request that carries `page[before]` — falls to the sentences after it: "In all other cases, a server **SHOULD** set these links to `null` when it can inexpensively determine that the current response is for the first or last page respectively", and "if the server can't easily determine whether there are … subsequent results (when computing the `next` link), it **MAY** use a URI in these links that returns an empty array as its paginated data." The kit never adds `page[before]`: its first request sets only a page size, and every later request is a `next` link exactly as the server wrote it, which the profile's own examples spell with `page[after]` alone. So every page the walk reads `next` from falls under the profile's MUST, and a `next` there to an empty page fails under the profile as it does under the base specification. A server whose own `next` link carried `page[before]` would earn the MAY on the page it leads to; the kit does not recognise that case, and reads `next` as the base specification defines it. A page whose `data` holds items but none with a string `type` and `id` (or `lid`) is not taken for an empty page. The kit cannot say what such a page lists, so the walk is reported not decided. The page is not counted as empty. A walk that would start on such a page — the reference or the second walk — is not begun, and the collection is reported not decided, since nothing such a walk found could be held against resources the kit never saw.

The walk is bounded in requests, so a hostile or broken pager cannot keep the kit walking forever or make the rule die: 20 pages per walk, 200 requests per run of the rule (the `first` / `last` checks and the order recheck below included), and a `next` that leads back to a visited page, or to a page adding no resource not already seen, ends it with a finding. It is bounded in time by `requestTimeout` (§1.5, thirty seconds unless the run says otherwise), which bounds each of those requests; a run that turns it off is held by a server that holds one response open, as for every other rule. A request the timeout cuts short is a lost response, so it leaves the collection not decided. `skip: ["spec/pagination/links-enumerate-collection"]` leaves the walk out altogether (§1.5). A collection the budget runs out on, at any of those requests, is reported not decided, naming the budget. It is never a partial pass. A server error, a `429`, a `408` (RFC 9110 §15.5.9: the server "did not receive a complete request message within the time that it was prepared to wait") or a lost response mid-walk, or from a `first` / `last` link, says nothing of the links, so it leaves the collection not decided, as it does for the reference request. A `next` that leads to any other 4xx, or to a 2xx that is not a page, is a finding. A link resolves against the page that carries it, and one that leads to another origin is not followed (`Skipped`, naming the origin). Server values in findings render as `resourceLabel` and `Formatter.format` render them ([#284](https://github.com/thomasfosterau/effect-jsonapi/pull/284)), so a link that is `{"toString":1}` is a finding, not a dead rule.

**An unstable order is not a violation of the links.** §Sorting: "The server **MAY** apply default sorting rules to top-level `data` if request parameter `sort` is not specified" — without `sort`, JSON:API requires no stable order, so offset pagination over rows that shift between requests may repeat or skip a resource without any link being wrong. So when the walk finds a problem that depends on order (a resource repeated or never reached, a `first` / `last` page that disagrees), the kit asks for each walk's first page again; if one comes back in a different order, those findings are withheld and the collection is reported not decided, quoting §Sorting. A recheck the budget leaves no request for, or that gets no page back, confirms nothing, so it withholds them too. This holds on every path out of the rule, including a walk cut short. The order-independent findings — `prev` on the first page, a `next` that cycles, dangles or is not a link — stand either way. Over an order that two identical requests reproduce, a repeat or a gap means `next` was not "the next page of data", so the rule is a MUST, the spec's own level. A server whose collection changes during the walk (a live server under writes) can show the same symptoms; the finding names the pages so they can be compared.

The rule skips, saying which, when no list or related endpoint declares a page size, when a collection holds fewer than two resources (no page size forces a second page), when the server answers every resource on one page at the size the kit asked for (it does not page at that size), or when the reference request is not answered 2xx with a resource collection the kit can identify. It costs about six to ten requests per collection.

**Links (§Resource Links, §Related Resource Links, §Fetching Resources, §Fetching Relationships)** — seven rules that follow the server's own links ([#168](https://github.com/thomasfosterau/effect-jsonapi/issues/168), [#309](https://github.com/thomasfosterau/effect-jsonapi/issues/309)), because nothing in the type system ties a link _string_ to the route that serves it: a refactor that moves a path leaves every emitted link pointing at a 404 while every test that asserts on the document still passes.

| Rule | Level | Follows | Expects |
| --- | --- | --- | --- |
| `spec/links/resource-self-dereferences` | MUST | every resource object's `links.self` | the same `(type, id)` as primary data. §Resource Links: the links object "**MAY** contain a `self` link that identifies the resource represented by the resource object", and "A server **MUST** respond to a `GET` request to the specified URL with a response that includes the resource as the primary data." |
| `spec/links/related-dereferences` | MUST | every relationship's `links.related` | a 2xx with resource data as primary data: a resource object (an object with a string `type`), an array of them or `null`. §Fetching Resources: "A server **MUST** support fetching resource data for every URL provided as: … a `related` link as part of a relationship-level links object"; §Related Resource Links: "If present, a related resource link **MUST** reference a valid URL, even if the relationship isn't currently associated with any target resources." |
| `spec/links/related-matches-linkage` | SHOULD | the `links.related` of every relationship that also carries linkage (`data`) | the resources the linkage names. §Related Resource Links: "A "related resource link" provides access to resource objects linked in a relationship. When fetched, the related resource object(s) are returned as the response's primary data." |
| `spec/links/relationship-self-dereferences` | MUST | every relationship's own `links.self` (the relationship link) | a 2xx with resource linkage as primary data: `null`, a resource identifier object or an array of them — identifier objects only — of the cardinality the relationship's linkage shows. §Fetching Relationships: "A server **MUST** support fetching relationship data for every relationship URL provided as a `self` link as part of a relationship's `links` object", and "The primary data in the response document **MUST** match the appropriate value for resource linkage". |
| `spec/links/relationship-self-matches-linkage` | SHOULD | the `links.self` of every relationship that also carries linkage (`data`) | the identifiers the linkage names. §Relationships, of the relationship link: "When fetched successfully, this link returns the linkage for the related resources as its primary data." |
| `spec/links/top-level-self-dereferences` | MUST | every document's top-level `links.self` | a 2xx with resource data as primary data. §Fetching Resources: "A server **MUST** support fetching resource data for every URL provided as: a `self` link as part of the top-level links object …". |
| `spec/links/top-level-self-matches-document` | SHOULD | every document's top-level `links.self` | a document of the same kind (below). §Document Top Level: `self` is "the link that generated the current response document". |

The levels follow the keywords. The `self` rule is the spec's own MUST sentence. For `related`, the MUST is §Fetching Resources' "support fetching resource data", so `related-dereferences` holds a link only to answering resource data. Which resources it must answer is §Related Resource Links' definition, which is declarative ("are returned") and carries no keyword, so `related-matches-linkage` grades it SHOULD (owner decision on [#312](https://github.com/thomasfosterau/effect-jsonapi/pull/312), 2026-10-09). The two follow the same links and are never both failed by one: a `related` link that does not parse, answers a non-2xx or answers something other than resource data is `related-dereferences`' finding, and `related-matches-linkage` leaves it not decided, naming that rule. The two `self` links split the same way (owner decision on [#309](https://github.com/thomasfosterau/effect-jsonapi/issues/309#issuecomment-6190325231), 2026-10-15). For a relationship's `self`, the MUST is §Fetching Relationships' "support fetching relationship data" and "**MUST** match the appropriate value for resource linkage", which `relationship-self-dereferences` reads as the answer's _shape_: resource linkage, identifier objects only, as many as the relationship holds. Which identifiers it names is §Relationships' definition of the relationship link ("returns the linkage for the related resources"), which carries no keyword, so `relationship-self-matches-linkage` grades it SHOULD. For the top-level `self`, the MUST is §Fetching Resources' "support fetching resource data", so `top-level-self-dereferences` holds the link only to answering resource data; that the answer is the same document comes from the definition of top-level `self` (the link that _generated_ the document), which carries no keyword either, so `top-level-self-matches-document` grades it SHOULD and holds it only as far as that definition settles it (below). As for `related`, each SHOULD leaves a link its MUST fails — one that does not parse, answers a non-2xx, or answers something its MUST rejects — not decided, naming that rule, so one broken link is never failed twice.

The links are collected from one `GET` of every read endpoint whose URL resolves (list, single-resource and related endpoints; a relationship endpoint answers identifiers, which carry none — though its document carries a top-level `self`, so `top-level-self-dereferences` searches relationship endpoints too), from primary data and any `included`. A link may be a string or a link object's `href` (§Links: "a link **MUST** be represented as either: a string whose value is a URI-reference …, a link object or `null` if the link does not exist"); one that is neither is a finding, rendered as `Formatter.format` renders it. Each link is resolved against the document that carries it and followed once: a link to a URL the rule already fetched (an article's `self` on the article's own endpoint, say) costs no request. What the answer is held to:

- **`self`**: a 2xx whose `data` is a resource object of the same `type` and `id`.
- **`related`** (`related-dereferences`): a 2xx whose primary data is a resource object, an array of them or `null`, whatever the linkage says. A resource object is an object with a string `type`, so `{"data":"x"}`, `{"data":["x"]}` and `{"data":[{"id":"1"}]}` are findings. A links-only relationship (as every `Relationship.paginated` is) has nothing more to be held to.
- **`related`, to-one linkage** (`related-matches-linkage`): that resource as primary data; for `null` linkage, `null`.
- **`related`, to-many linkage** (`related-matches-linkage`): the same set of identities, with no order. A side that is a page relaxes it to a subset: when the answer carries `next` (the related collection pages), every resource it lists must be in the linkage; when the relationship carries `next` (the linkage pages — §Relationships: "Any pagination links in a relationship object **MUST** paginate the relationship data, not the related resources"), every resource the linkage names must be in the answer. When both are pages, nothing can be compared, and the link is not decided.
- **A relationship's `self`** (`relationship-self-dereferences`): a 2xx whose primary data is resource linkage — `null`, a resource identifier object, or an array of them. A resource identifier object is an object with a string `type`, a string `id` or `lid`, and no member but those and `meta` (§Resource Identifier Objects), so a full resource object — one carrying `attributes`, `relationships` or `links` — is a finding, naming the first member that does not belong. The cardinality must be the relationship's: when the relationship object's linkage is `null` or one identifier (to-one), the answer must be `null` or one identifier; when it is an array (to-many), an array. A links-only relationship (every `Relationship.paginated`, through `Handlers.paginatedRelationship`) shows no cardinality, so it is held only to answering linkage of either kind.
- **A relationship's `self`, against its linkage** (`relationship-self-matches-linkage`): when the relationship object carries linkage (`data`), the answer is compared with it exactly as `related-matches-linkage` compares a `related` answer: the same identifier for to-one, `null` for `null`, and for to-many the same set of identities in any order, relaxed to a subset when either side carries `next`, and not decided when both do. An identifier named only by `lid` cannot be compared, so it leaves the link not decided.
- **The top-level `self`** (`top-level-self-dereferences`): a 2xx whose primary data is resource data — a resource object, an array of them or `null`, as for `related`. A relationship endpoint's identifiers are objects with a string `type` too, so its document's `self` holds.
- **The top-level `self`, against its document** (`top-level-self-matches-document`): a document of the same kind as the one carrying the link. A single resource must answer that resource (the same `type` and `id`); `null` primary data must answer `null`; a collection must answer a collection (an array as primary data). A collection is compared resource for resource — the same set of identities, in any order — **only when neither document carries a `next` or `prev` link**: a page, on either side, may legitimately list other resources than the document it is compared with (the window moved, the server added a default page size to the `self` it wrote, or the order is unstable), so a page is held only to answering a collection. Order is never compared. Most servers write the URL that was requested as the `self`, which the rule has already fetched, so such a link costs no request and holds; the rule earns its keep when a server writes a `self` that differs from the request — a canonicalised query, a path the router no longer serves.

**What the kit cannot identify, it does not decide on, on either side.** An answer listing an item without a string `type` and `id` leaves the link not decided. So does a claim the kit cannot read: a resource object with no string `type` and `id` cannot have its `self` held to it, and linkage naming such an item cannot have its `related` held to it. Such a link is noted as not decided, without a request, rather than dropped (the `self` case) or compared with the unidentified item left out (the linkage case, which would report a resource the linkage does name as one it does not).

The crawl is the pagination walk's (`src/internal/conformance/crawl.ts`, shared): `GET` only, and a link that leads to another origin (scheme, host or port) is never requested and is reported not followed; one whose scheme gives it no origin (`javascript:`, `data:`) is named by its scheme. A redirect is followed only within the base URL's origin (§1.2), each hop counting against the budget, and the answer it leads to is what the link is held to; one the kit does not follow — off the origin, past five hops — leaves the link not decided and the rule `Skipped`, naming its `Location` (§1.2), so a link cannot reach another origin that way either. A server error, a `429`, a `408` or a lost response leaves that link not decided, never failed. So does a `401` or `403`: access control is outside JSON:API, so a link the kit may not follow is not a broken one. Any other non-2xx — a `404`, or a `3xx` with no `Location` to follow — is a finding: the run has just received the link from the server, so a 404 for it is the server contradicting itself (a live server under writes can legitimately delete a resource between the two requests; the finding names both, so they can be compared). Each rule may make 200 requests per run, the collecting `GET`s included. A crawl the budget cannot finish — a read endpoint it had no request left to search, or a link it had none left to follow — is `Skipped`, naming the budget and how far it got, never a partial pass, unless a link it did follow already broke the rule, which stands. Like the pagination walk, the crawl is bounded in requests, and in time by `requestTimeout` (§1.5) unless the run turns it off; a request the timeout cuts short is a lost response, which leaves its link not decided. `skip: ["spec/links/"]` leaves the crawl out altogether (§1.5). A rule that decided some links and not others passes with a note naming each it could not decide; with none decided it skips, saying why. With no link to follow it skips, naming the endpoints it searched and how each that did not answer 2xx answered. A failed rule lists its first ten findings and one more counting the rest, and every server value a finding names — a resource's `type:id` included — is quoted cut to 200 UTF-16 code units, so a server with a broken link on every resource, or an id a megabyte long, does not make a report of the same size.

**Status codes** — 404 for an absent resource. With the write fixture (§1.4): a creation without a client-generated id answers 201 with the created resource as primary data (`create-response-document`); the 201 carries `Location` (`create-location`, a SHOULD — the spec's level, corrected from the MUST the never-run v1 rule claimed) and, when the resource also carries `links.self`, the two match (`create-location-matches-self`); an update answers 202, 200 with a document whose primary data — when it has any — is the updated resource (JSON:API 1.1 lets a 200 carry no primary data when the server changed nothing beyond the request; the document must then still be one, so the kit wants a top-level `meta` and no `errors`), or 204 with no response document (`update-response`); and a delete answers 204 empty, 200 with only `meta`, or 202 (`delete-response`).

**Atomic operations** — a malformed `atomic:operations` document is rejected; with the write fixture, an `add` of the fixture's payload is answered under the extension's media type (`response-ext-parameter` — a §Content Negotiation universal-responsibility MUST: whoever applies an extension names it in `ext`). `lid` resolution and all-or-nothing are declared and skipped; see §5.

**The profile tier** — the filter grammar's advertisement (§5), its rejections with `source.parameter` (§2, §4, §7: an operator outside the closed core, an undeclared field, a key deeper than the grammar admits, a repeated `filter[…]` key), and spelling equivalence (§2.2, §3: bare shorthand, explicit `[eq]`, group form and a key-permuted group form must all answer the same document, because the canonical string is a function of the AST alone). The Idempotency-Key profile's advertisement (`docs/idempotency.md` §1, a SHOULD): with the write fixture (§1.4), one create per create endpoint that declares `Idempotency-Key`, and one create plus one update (the `update` fixture) per update endpoint that declares it — at most one create and one update per type, the create judged too when its endpoint declares the header. Each 2xx must name the profile URI in `jsonapi.profile` (what `Idempotency.jsonapi` produces) or in the media type's `profile` parameter; either passes, since §1 makes the media type a MAY. A media type naming it passes even with no body; a write the server does not accept, or a 2xx with no document whose media type does not name it, decides nothing. The kit sends a fresh `Idempotency-Key` only to an endpoint that requires one (`idempotency: "required"`), as every write rule does; where the key is optional it sends none ([#165](https://github.com/thomasfosterau/effect-jsonapi/issues/165)). Plus two library conventions: advertising `jsonapi: { version: "1.1" }` ([#103](https://github.com/thomasfosterau/effect-jsonapi/issues/103)) and accepting the repeated-key spelling of every comma-separated family ([#102](https://github.com/thomasfosterau/effect-jsonapi/issues/102)).

The grammar rules learn a field name the target is known to accept from a baseline response before probing rejections — otherwise "undeclared operator" would pass for the wrong reason, since an undeclared _field_ is also a 400.

## 4. Vacuous passes are the failure mode

A conformance kit that answers "OK" without saying what it checked is worse than nothing, because it manufactures confidence it has not earned. Three mechanisms guard against it:

1. **Applicability gating.** A conditional rule that never met its condition reports `Skipped`, not `Passed`. `spec/document/full-linkage` over an api that returned no compound document says so; `spec/document/jsonapi-object` over documents with no `jsonapi` member says so; `spec/query/sparse-fieldsets-included` counts only projection probes that actually returned an `included` resource of the requested type.
2. **Three distinct kinds of "not checked".** A rule can be absent because this api has no endpoint of that shape, because the caller withheld a sample id, or because the kit does not implement it at all — and the report keeps them apart. A reader who cannot tell them apart does not know what the run proved.
3. **A declared coverage ledger.** `Conformance.gaps` lists the areas the kit does not check, each with its reason and its tracking issues, and `format` prints it in every report. A requirement named neither in `Conformance.rules` nor in `Conformance.gaps` is simply unwritten, and the ledger says so in as many words.

The summary line reports skips alongside passes for the same reason:

```
SUMMARY  7 rules failed (19 findings) · 19 passed · 10 not checked · 7 areas out of scope · 111 requests made
```

### 4.1 The four outcomes

Every rule in a run ends in exactly one `Conformance.Outcome`, and the four mean different things:

| Outcome | Means | Is it a verdict on the server? |
| --- | --- | --- |
| `Passed` | The rule ran, made its probes (`probes` counts them) and found nothing. | Yes: it held. |
| `Failed` | The rule ran and found the server breaking it; `findings` says how, with the request. | Yes: it is broken. |
| `Skipped` | The rule could not be decided against this target — no endpoint of that shape, a withheld `ids` sample or `writes` key, a condition never met (§4 above), a write payload the server rejected or a `writes` `create` / `update` that threw — and `reason` says which. | No: a statement about coverage. |
| `Errored` | The rule **died** before it reached a verdict: a transport that throws, or a bug in the kit. `message` renders the defect and `defect` is the value as thrown. | No: the run could not decide it. |

A rule that skips was _never going to_ be decided against this target; a rule that dies _should have been_ and was not. A throwing fixture is neither: a `create` or `update` that throws skips the rules it was for, naming the member, and a `cleanup` that fails or throws is recorded in `Report.writes` as `cleanup-failed` (§1.4). Since [#246](https://github.com/thomasfosterau/effect-jsonapi/issues/246), a rule's defect is that rule's `Errored` outcome rather than the end of the run: every other rule still runs and is reported, and so is `Report.writes`, so the cleanup ledger survives one bad rule. (Before, the defect failed the whole `verify` / `verifyWith` and took the rest of the report with it.) Interruption is not turned into an outcome — it is a request to stop the whole run, not something one rule did, so it still stops it.

How each reading of a report treats it:

- **`format`** prints each tier's dead rules first, marked `DIED`, with the defect's message in place of findings. The tier and summary lines gain a `· N died` count — only when a rule did, so a clean run's summary reads as above.
- **`summarise`** counts them in `errored`, separately from `failed`, `passed` and `skipped`.
- **`assert`** dies on the first `Errored` outcome, before it looks at failures, with a defect that names the rule and carries the original defect as its `cause`. It does not fail with a `ContractViolation`, because a dead rule is not a finding about the server, and it cannot pass, because the rule was not decided — so a gate built on `assert` is exactly as strict as when a defect killed the run.
- **A gate that does not use `assert`** must check for dead rules itself. A test that filters `outcomes` for `Failed` — for instance to pin a known set of failures, as this repo's examples do (§8) — lets an `Errored` rule through silently. Gate on `Conformance.summarise(report).errored === 0` as well, and print `Conformance.format(report)` when it is not.

## 5. What v1 does **not** cover

Declared in `Conformance.gaps` and printed in every report.

| Area | Why not |
| --- | --- |
| **The filter profile's evaluation semantics** | Whether `not(eq(status, x))` matches a NULL row, whether `nin` is SQL's `NOT IN` or the negation of `in`, where an absent attribute lands. Needs an oracle over known data, which a black-box transport cannot supply. See §6. |
| **Sort ordering correctness** | That an unsupported field is a 400 is checked; that `?sort=-createdAt` actually orders, and where NULLs land, needs known data and the profile's collation decision. |
| **Write semantics beyond the success responses** | The write fixture (§1.4) covers what a successful create, update and delete answer. Still unwritten: the 409 Conflict rules, creation with a client-generated id, relationship mutation through `/relationships/…`, and reading a write back to confirm it was stored ([#237](https://github.com/thomasfosterau/effect-jsonapi/issues/237)). |
| **Atomic operations processing** | `lid` resolution, all-or-nothing, `atomic:results` ordering — these need operations applied and then observed, and all-or-nothing a deliberately-invalid operation the fixture does not supply ([#164](https://github.com/thomasfosterau/effect-jsonapi/issues/164)). |
| **The Idempotency-Key profile** | Its advertisement is checked on create and update endpoints (§3). Delete endpoints (usually a 204, with no document to name it in) and the atomic operations endpoint are not checked. What a retried write does — replay, the fingerprint mismatch, the in-flight case, the scope of a key — needs the kit to resend a request byte for byte ([#162](https://github.com/thomasfosterau/effect-jsonapi/issues/162), [#165](https://github.com/thomasfosterau/effect-jsonapi/issues/165)). |
| **Concerns outside JSON:API** | Auth, caching, conditional requests, rate limiting, CORS. The spec takes no position, so neither does the kit. |

Mutating probes are **off by default** (`mutating: true` opts in, and the write rules also need a `writes` fixture), because a conformance run should be safe to point at a live server.

## 6. Relationship to #116

[#116](https://github.com/thomasfosterau/effect-jsonapi/issues/116) completed the filter profile by giving it normative semantics, and **landed while this kit was being built**. The two were coupled but not ordered, because the profile splits cleanly along the line the kit can see:

- **Normative all along, and checked here.** `docs/filter-grammar.md` §2 (surface syntax and what is a 400), §3 (canonical encoding and the round-trip invariants), §4 (the closed operator core), §5 (the profile URI and its advertisement) and §7 (`source.parameter` on every rejection). None of these needs to know what a tree _means_, so all of them are in the profile tier today, and were before #116 landed.
- **Semantic, and a different kind of rule.** What §1.3 used to defer to a citation is now `docs/filter-grammar.md` §6: three-valued Kleene logic, a truth table per operator, and comparison defined on the field's JSON representation — rule-identified `F-EVAL-*`, `F-CMP-*`, `F-IN-*`, `F-LOGIC-*`, `F-ISNULL-*`, `F-NULL-*`, `F-CONS-*`. Deciding these means knowing which resources the server holds and what each one should have matched.

### 6.1 What #116 handed to this kit

#116 decided **no reference evaluator ships**, and said why the oracle belongs here instead:

> An executable oracle belongs where it can run against the thing that actually has to conform — a **server** — which is the conformance kit, #120. […] checking a _server_ against them is #120's job.

It also observed that the harness already holds the input: F-ORD-1 defines comparison on a field's **JSON representation**, and F-EVAL-4 reads `value(resource, field)` from it — which is exactly what a probe gets back off the wire. So the gap is narrower than it was first written. The remaining work is:

1. A fold over `Filter.Ast` implementing §6.3's tables (short, per #116, but a second implementation of §6 to keep honest — which #116 names as a real cost).
2. A rule that fetches a collection unfiltered, evaluates a filter tree over each returned resource's JSON, and compares the expected match set against what the filtered request actually returned. No seeded fixture needed — the unfiltered collection _is_ the known set.

### 6.2 The open decision

Whether that evaluator is **public API or internal to the kit**. #116 left it open —

> Revisit if #120 wants the evaluator as a shared building block rather than a fixture of its own.

— and it is a real choice, not a detail. Public, it is the first thing this package ships that evaluates data rather than describing it, and F-ORD-1's comparison domain (derived internally from an attribute's encoded form, deliberately not part of `Resource.filterable`'s public shape) would have to be exposed. Internal, the kit keeps its own oracle and no new public surface appears, but a consumer building a server cannot reuse it to check their own store.

That decision is deliberately **not** taken in this version. The gap stays declared, now pointing at §6 and at this question rather than at an unlanded issue.

## 7. Shipping

`Conformance` is a module of the package, namespaced from the root like every other:

```ts
import { Conformance } from "@thomasfosterau/effect-jsonapi";
```

A **supported entry point**, not a dev-only fixture: it compiles to `dist` and ships, so a consumer can run it. (`effect-auth#199`, where the in-memory server fixture is excluded from the build and so unusable downstream, is the cautionary tale #120 cites.)

Two packaging questions are deliberately **not** pre-empted:

- **[#117](https://github.com/thomasfosterau/effect-jsonapi/issues/117) (subpath exports).** `Conformance` imports `effect/http` and `effect/http-api`, so it is unambiguously in the HTTP tier wherever #117 draws the line. Adding a subpath now would pre-empt a decision #117 wants made deliberately.
- **[#121](https://github.com/thomasfosterau/effect-jsonapi/issues/121) (`sideEffects`, `src` in `files`).** The module is pure — rule data and functions, no top-level effects — so it is compatible with `sideEffects: false` whenever that lands.

## 8. Running it against this repo

`examples/{blog,github,northwind}/test/conformance.test.ts` run the kit against all three worked examples, with `mutating: true` and a write fixture for every type with a create endpoint (`articles`; `repositories` and `issues`; `products` and `orders`) whose `cleanup` removes the resource from the example's in-memory store. Each asserts the write rules ran and nothing was left behind. Rather than assert a clean run, each pins the exact set of rules its example is known to break, with the issue tracking each (`KNOWN_FAILURES`) — and that set is now **empty** in all three: every rule the kit runs against the examples passes, or is skipped with its reason.

All three pass `spec/links/related-dereferences`, following the `related` link `Handlers.paginatedRelationship` builds for each paginated relationship (an article's comments, an issue's comments, an order's line items) to a collection; a deliberately broken `paginatedRelationship` (a `related` path no route serves) fails the rule in all three. All three skip `spec/links/related-matches-linkage`: the only relationships carrying a `related` link are those paginated ones, which are links-only, so no linkage can be compared. All three skip `spec/links/resource-self-dereferences`: no resource object a read endpoint answers carries `links.self` (only the resources the create handlers answer do), so there is no link to follow — an example gap, not a failure. All three pass `spec/links/relationship-self-dereferences`, following the `self` link `Handlers.paginatedRelationship` builds to the relationship endpoint, and skip `spec/links/relationship-self-matches-linkage`, because that relationship is links-only; and all three pass `spec/links/top-level-self-dereferences` and `spec/links/top-level-self-matches-document`, following each read endpoint's top-level `self`. Each example's conformance test pins those four outcomes. The relationship rule found that the github and northwind examples linked to relationship endpoints they did not serve (`/issues/:id/relationships/comments`, `/orders/:id/relationships/lineItems` answered 404); both now declare a paginated `Endpoint.getRelationship` for it, as the blog example already did for an article's comments.

All three pass the seven [#310](https://github.com/thomasfosterau/effect-jsonapi/issues/310) rules, each probing a single-resource fetch for an undeclared `fields[TYPE]`, `page[…]` or `filter[…]` and a collection for an undeclared `page` / `filter` member and a bracketed `include[]` / `sort[]`, every one answered by `Middleware.SchemaErrors`; the 45 rules before them decide exactly as they did.

All three pass `spec/pagination/links-enumerate-collection`, walking their paginated collections — offset pagination in the blog and Northwind, page-number pagination in the GitHub example (whose `/search` pages by offset) — through the links `Handlers.offsetPaginationLinks` and `Handlers.numberPaginationLinks` build. The blog and GitHub examples each note the one collection they could not decide, a collection of one resource (`/articles`, `/pulls`); Northwind decides every collection it walks, `/orders/10248/lineItems` included, now that its fixture samples ids the example holds ([#301](https://github.com/thomasfosterau/effect-jsonapi/issues/301)). A deliberately broken `offsetPaginationLinks` (a `next` that skips a page) fails the rule in all three.

Eight rules were on this list until their fixes landed, and the kit now guards them instead. Five were library defects: [#236](https://github.com/thomasfosterau/effect-jsonapi/issues/236), found by the write fixture the first time `create-location` ran (no 201 carried `Location`, because nothing in the library emitted one; `Endpoint.create` now attaches `Middleware.CreatedLocation`, which copies the created resource's `self` link into the header, and the examples give each created resource its own `links.self`, so `create-location` passes and `create-location-matches-self` runs and passes rather than skipping — both are among the write rules each example asserts passed); [#101](https://github.com/thomasfosterau/effect-jsonapi/issues/101); [#102](https://github.com/thomasfosterau/effect-jsonapi/issues/102) (the repeated-key spelling was honoured for `include` only); [#147](https://github.com/thomasfosterau/effect-jsonapi/issues/147), found by the kit (`Handlers.buildIncluded` did not dedupe `included` against the primary data, so a heterogeneous collection's `/search?include=…` repeated a hit in `included`); and [#148](https://github.com/thomasfosterau/effect-jsonapi/issues/148), also found by the kit (a query parameter named only with a-z that the endpoint does not process was ignored rather than rejected; `Middleware.SchemaErrors` now answers it with a 400 naming it in `source.parameter`).

The last three, failed by all three examples alike, were _example_ gaps rather than library ones: `spec/query/sparse-fieldsets-primary` and `spec/query/sparse-fieldsets-included` ([#112](https://github.com/thomasfosterau/effect-jsonapi/issues/112) landed `onResource` / `Handlers.project`), and `profile/document/jsonapi-member` ([#103](https://github.com/thomasfosterau/effect-jsonapi/issues/103) landed the `jsonapi` builder option). The examples adopted both in [#169](https://github.com/thomasfosterau/effect-jsonapi/issues/169): the reads that already declared `fields` — each example's `/search` and its single-resource fetches with `include` (`GET /articles/:id`; `GET /repositories/:id` and `GET /issues/:id`; `GET /products/:id` and `GET /orders/:id`) — project every resource they answer, primary data and `included` alike, with `onResource: Handlers.project(query.fields)`, and every `Handlers.data` / `collection` / `linkage` call passes `jsonapi: Document.v1_1` (the blog's `Atomic.results` answer to `/operations`, like the `ApiError` error documents, carries no `jsonapi` member). That also gives `spec/document/jsonapi-object` a `jsonapi` member to check, so it now passes in all three rather than skipping. The other reads still declare no `fields`, deliberately: declaring it makes a client read every attribute of that endpoint's resources as optional ([#322](https://github.com/thomasfosterau/effect-jsonapi/issues/322)), and the kit's two sparse-fieldset rules probe every endpoint that declares `fields[TYPE]`, so the endpoints above already decide both — a fetch with `include` gives `spec/query/sparse-fieldsets-included` an `included` resource to project.

A new failure means a regression; a disappearing one means a fixed bug whose entry should come off the list. The test says so when either happens.

Pinning failures is not `assert`, so each example also asserts that **no rule died** — in the full run and in the spec-tier-only run — listing every dead rule as `id: message`, with the whole report in the failure message (§4.1). Without it, a rule that dies would drop out of the `Failed` filter and the suite would stay green over a rule it never decided.

## 9. Proving the kit detects

A kit that finds nothing is indistinguishable from a kit that checks nothing, so `Conformance.test.ts` drives it against a **canned transport**: a hand-written JSON:API server good enough to pass every rule the kit can decide, and then ~20 one-line deviations from it, each breaking exactly one rule.

Each case asserts the kit reports that rule _and_ produces a finding with a non-empty expected and observed. One further case asserts the converse and matters just as much:

```ts
it("does not flag anything else when one rule is broken", async () => {
  // …serve `application/json` instead of the JSON:API media type…
  expect(failed(report)).toEqual(["spec/content-negotiation/response-media-type"]);
});
```

A kit that fails everything catches every bug and is worthless. The control — the conformant server, against which the kit reports no failures — is the other half of the same argument.

**The two rules for a family an endpoint does not declare get their own api**, because the main fixture declares `include` on every read endpoint: `get` without `include` beside a `list` that declares `include` but not `sort`. Against a canned server that refuses both, each rule passes having probed its endpoint; a server that ignores `include` there fails the include rule alone, one that ignores `sort` fails the sort rule alone (the main fixture's `list` carries a `broken(…)` case for it too), and a 422 fails both. A 400 whose `source.parameter` blames another parameter fails; one with no `source` passes with its note. A 400 carrying no error objects passes with a note that says so. A probe answered 500 or 503 fails both, as not rejected; one answered 429 or 408, or not at all, leaves both not decided, naming what answered ([#352](https://github.com/thomasfosterau/effect-jsonapi/issues/352)), and one a transport redirected off the origin leaves the include rule not decided with its own reason beside the redirect `runRule` names. The skips are pinned — every read endpoint declaring `include`, no endpoint without it resolving, every list declaring `sort`, every baseline failing (naming each status) — and so is the scope: a to-one related endpoint answering one resource is never sent `sort`, and one discovered before a list is passed over for that list, which is then probed; a read endpoint whose baseline fails is passed over for the next. Hand-built endpoints whose query is a union or a suspended schema declaring the family are not probed, and one whose query is a record is not probed at all. Two in-process cases hold the real middleware to the same 400s, and the write fixture's server now refuses `include`, which its api declares nowhere. Over twenty-one list endpoints declaring nothing, each baseline a 500, both rules stop at the 20-request budget they share with the rules below, trying nineteen and skipping, naming the endpoints left untried.

**The seven rules for a family or member an endpoint does not declare get an api of their own too** ([#310](https://github.com/thomasfosterau/effect-jsonapi/issues/310)): `get` declares no query, so it must refuse `fields[articles]`, `page[limit]` and `filter[title]`; `list` declares the bare `include` and `sort`, offset page keys and `filter[title]`, so it must refuse `include[]`, `sort[]`, `page[offset_x]` and `filter[title_x]`. Against a canned server that refuses each, naming it, every rule passes with one baseline and one probe, and the probes sent are pinned, so none is a name the endpoint declares; a server that drops one of them fails that rule alone, and a 400 blaming another parameter fails. A probe answered 500 or 503 fails every rule; one answered 429 or 408, or not at all, leaves every rule not decided, and so does one a transport followed off the origin itself, without saying a lost response says nothing. Discovery is pinned: a derived member steps past a declared `title_x` to `filter[title_x_x]`; `fields` is never sent for a type the endpoint declares; `filter: true`'s grammar and a hand-built open `filter[…]` or `page[…]` record count as declaring their family; a hand-built query that declares `include[]` or `sort[]` beside the bare parameter is never sent the bracketed one; and a type or attribute name a baseline shows that would need encoding (`a b`) is passed over for one that goes into a parameter as itself, or for the placeholder (`filter[x]`). The skip reasons are pinned. So is the budget: twenty-one endpoints whose baselines answer 500 get nineteen requests and a skip, and when each baseline is a same-origin `302` to a 500, the redirects count, so nine endpoints and the tenth's unfollowed `302` spend nineteen requests, not thirty-eight.

**The write rules get their own fixture too**: an api with create, update, delete and atomic operations endpoints and a canned server whose writes land in a `MutableHashMap`. Against it every write rule must pass and actually run, and the store must end empty; then each rule is broken in turn (a 200 for a creation, a 201 without the created resource or without `Location`, a `Location` that disagrees with `links.self`, an update answering a different resource, a 200 DELETE carrying `data`, an atomic response without the `ext` parameter), each asserting **exactly** that rule fails. A 200 update with no primary data and a top-level `meta` must pass; one answering `{}`, an `errors` document (with or without `meta`), a `meta` that is not an object, `data: null` or no document at all must fail, each with a finding that says which. Further cases pin that the kit refuses an id it evidently did not create: a create answer naming a resource of another type, naming the `ids` sample, naming an id a read earlier in the run returned (as primary data, only in `included`, or only as to-one or to-many linkage), naming an id the run already holds a live record for, and naming `..`, `.`, `""` or a lone surrogate — in each, no PATCH, no DELETE and no `cleanup` reaches that id (for the unsafe segments, no PATCH or DELETE is sent at all), and the record says what was named. Others show that an id the server reuses after the kit removed its first holder is still accepted, even when a read-back of the first holder showed it (`src/internal/conformance/write.test.ts`); that what an unsuccessful read carries is not counted as shown; and that every rule that creates nothing, the profile tier's included, sends its requests before the first create while the report keeps the suite's order. The parameterised-`Content-Type` rule is run against a server that ignores the media type and applies whatever it can, and must fail it while having sent nothing it could apply; two more apis pin where it sends that probe — to the create endpoint even when an update and a relationship write are discovered first, and, with no create endpoint, to the update before the relationship write. The contract itself is pinned too: nothing is written without `mutating: true`; a missing fixture or sub-key skips naming the key; a rejected payload skips rather than passes; cleanup runs after a rule that fails and after one that dies; a failing cleanup is recorded without aborting the run; and with no `cleanup` the report lists what it left.

**A target behind redirects** reuses the write fixture's server, every rule run with writes on, behind a transport that redirects every request ([#168](https://github.com/thomasfosterau/effect-jsonapi/issues/168)). When each redirect stays on the run's origin (a `308` to the same path under `/live`), every rule's outcome — verdict, findings, note and reason — is the same as against the server directly; only the request counts differ. When each leads off it (a `302` to another host, or to the same host over `https`), no request is sent there, `spec/target/reachable` fails with one finding naming the `Location` and telling the caller to point `baseUrl` at the URL that serves, no other rule fails or passes, and a create the kit could not read is named by its redirect. When only some requests leave the origin, a rule that sent one is skipped rather than passed on the rest: only the `DELETE` redirected skips `spec/status/delete-response`, and only the requests carrying a query string skips `spec/query/include-unsupported-endpoint`, while a 404 that is no error document still fails `spec/errors/error-document-shape` beside a redirected `?unknown=1`, and `spec/errors/error-source-discrimination`, skipping for want of an error `source` once `?unknown=1` is redirected, names the redirect after its own reason. The pagination walk skips, never passes, a collection it walked beside one whose `next`, or whose every request, left the origin. Behind a transport that follows each redirect itself (`HttpClient.followRedirects`), redirecting only `?unknown=1`, only the `DELETE`, only the `POST`s, or every request that carries a query leaves every rule with the outcome it has when the kit sees the redirect, whether the other origin answers or the transport fails there: the `spec/errors/*` rules skip rather than pass on 2 of 3 requests, `spec/query/unknown-query-parameter` and `spec/status/delete-response` skip rather than fail with "was not rejected" or "got no response", `spec/query/include-unsupported-endpoint` rather than fail with "was not rejected", and so do the seven unsupported-family and bracketed rules against a probe so followed, none of them saying a lost response says nothing ([#344](https://github.com/thomasfosterau/effect-jsonapi/issues/344)). A `303` on a `DELETE` or `PATCH`, or a `301` or `302` on a `POST`, that such a transport followed within the origin, turning the method into a `GET`, leaves every rule as it is when the kit sees the redirect and refuses it, and is named as such; a `307` it followed within the origin is read. When every request is so followed (answered or failing there), or every one redirects along a chain on the origin past the hop cap, or to a `Location` that does not parse, `spec/target/reachable` tells the caller to pass a client that does not follow redirects, to shorten the chain, or to fix the `Location`, not to move `baseUrl`. `undecidedByRedirects` is pinned in `src/internal/conformance/core.test.ts` too: a pass with no note, a note kept when every request was redirected, a finding with no probe kept, two identical redirected requests named once, and a rule's own skip given the redirect clause after its reason. Against six list endpoints, four of them redirected off the origin, `spec/target/reachable` names "4 of 6 read endpoints", and `spec/content-negotiation/response-media-type` skips naming three redirects, counting the fourth, and keeping its coverage note. `src/internal/conformance/core.test.ts` pins the runner and the budget: a `307` re-sends a `POST` and its body, a `302` or `303` does not turn a `POST` or `PATCH` into a `GET` but is followed for a `GET`, a `3xx` without a `Location`, or with an empty one, answers as itself, a `Location` that does not parse or has no origin is not followed, and each hop is a request, a chain the budget cannot finish answering nothing.

**The filter-grammar rules get their own fixture**, because nothing else would run them: no api in this repo declares `filter: true`, so against every example they legitimately report `Skipped`. A rule that skips everywhere would ship never having executed, which is indistinguishable from a rule that does not work. So `Conformance.test.ts` carries a grammar-enabled api and a canned server implementing §2/§4/§5/§7 correctly, asserts the three rules **pass and actually ran** (not skipped), and then breaks each in turn: the profile parameter dropped from the media type, an operator outside the closed core accepted, a rejection that omits `source.parameter`, and the group form answering a different document from the shorthand it desugars from.

**The pagination rule gets its own fixture**, because the main api declares no page size: a `tags` collection of seven, listed under `Query.Page.Offset`, `Query.Page.Number` and `Query.Page.Cursor`, and canned pagers for each that must pass — the cursor pager with opaque cursors and absolute `next` URLs, a fourth paging by default so the reference is a walk of its own — with the requests asserted, so a pass is shown to have walked. Then each way a pager breaks, one at a time, with the finding pinned: pages that repeat a resource, a skipped page (caught only against the reference), a `next` that cycles, one that never ends past the last page, one that serves the same page forever, `prev` on the first page, `last` past the end, `first` on the wrong page, a `next` leading to a 404 or to a 2xx that is not a page, one that is `{"toString":1}`, a walk that reaches a resource the reference does not list, and one that goes on past the collection's size (stopped there). A server value longer than 200 UTF-16 code units is quoted cut, never splitting a surrogate pair. The bounded cases assert the request count too. Ten collections ahead of `tags`, each spending an exact number of requests, pin the request budget of 200. With them, the budget runs out at a chosen request: before `tags` is fetched, mid-walk (not decided, never taken for a collection that ended there), at its `first` link, and at its order recheck. The skips are pinned: a `next` to another origin (never requested), a collection too long for the page budget, an endless `next` of fresh resources, a collection whose order shifts on every request (withheld, quoting §Sorting), a walk cut short to a repeat whose order then shifts, a 503, a 500, a 429, a 408 or a lost response mid-walk, each of those statuses from `first` or `last`, a 503 from the order recheck, a reference walk cut short to a repeat whose order then shifts (the recheck stopping at that first unstable page, its requests asserted), a page, a `first` page or a whole collection of items the kit cannot identify, a reference or a second walk that starts on such a page, no page size declared, a single resource, and a server that ignores the page size. An in-process case holds `Handlers.offsetPaginationLinks` and the real router to the rule.

**The link rules get their own server** (`linked` in `Conformance.test.ts`), because the main fixture's resources carry no links: two articles, each with a `self`, a to-one `author`, a to-many `tags` and a links-only `comments`, every link resolving to what it names. Each relationship also carries its own `self` link and each document a top-level `self`, served by the same server. Against it all seven rules pass, with the requests asserted, so a pass is shown to have followed each link once (a link to an endpoint already fetched costs nothing; `related-matches-linkage` does not follow the links-only `comments`). Then each way a link breaks, one at a time, with the finding pinned: a `self` that leads to another resource, to a 404 or to `data: null`; a `related` that answers something other than resource data (`related-dereferences`); and a `related` that omits a resource its linkage names, answers one it does not name, answers another to-one resource, or answers a resource where the linkage is `null` (`related-matches-linkage`, while `related-dereferences` passes the same answer). A `related` that answers 404 or is not a link at all fails `related-dereferences` once and is left not decided by `related-matches-linkage`, which skips when no relationship carries linkage. The subset relaxations are pinned both ways — a page of the related collection, and a page of linkage, each passing when it is consistent and failing when it is not — and two pages are not compared; nor are an answer, a resource or linkage holding an item without a string `type` and `id`. Link objects, a relative link (one that resolves differently against the document and against the base URL) and an absolute link to the run's own origin are followed; a link that is `{"toString":1}` is a finding; a link to another origin is never requested (every request is asserted to go to the run's origin) and is noted, or skipped when it is the only one; a `javascript:` link is named by its scheme. A `fetch` that would follow a redirect off the origin is never let to, even when the run's own `RequestInit` says `redirect: "follow"`, and the rule is skipped, naming the `Location`, never passed on the links that did decide; an `http` → `https` redirect on the same host is treated the same way, and so is a read endpoint redirected off the origin while every link it did find decides. A redirect within the origin is followed, its final answer graded (a different resource there is a finding) and its hop counted; a chain of five hops is followed and one of six skips the rule; a relative link in a redirected answer resolves against where the answer came from; and an answer a transport fetched from another origin all the same is not read, and skips the rule, naming where the transport ended up, rather than passing it on the links that did decide. A `related` answering `{"data":["x"]}`, `{"data":"x"}` or `{"data":[{"id":"1"}]}` is a finding; `{"data":null}` passes. A label the linkage names is quoted cut like any other. A 503, a 500, a 429, a 408, a lost response and a 403 leave the link not decided. The budget is pinned at exactly 200 requests over 250 articles (skipped, naming it), and over 201 read endpoints, one never searched (skipped, naming it, and not counting a read endpoint whose URL does not resolve as searched); a finding made before it ran out still fails the rule. Twenty-five broken links list ten findings and count the rest, and a 300-character id is quoted cut. The roles searched are pinned: a related endpoint's answer is, a relationship endpoint is never requested by the rules that look for links on resource objects. The skips name what they searched. For a relationship's `self` (#309): a pass following each of the six relationship links once (the SHOULD following the four that carry linkage); an answer that is no resource linkage, with linkage to compare and without (a links-only relationship); full resource objects where identifiers belong — to-one, to-many and links-only — and an identifier carrying `links` or `relationships`, each failing the MUST; an identifier with no string `type`, or with neither `id` nor `lid`, failing it too, while `meta` and a `lid` pass; linkage of the wrong cardinality, an array for to-one and one identifier for to-many, failing the MUST, while `null` for a to-one relationship passes it and fails only the SHOULD, and a links-only relationship takes either; linkage that omits an identifier the relationship names, names one it does not, or names another to-one identifier, each failing the SHOULD while the MUST passes; a 404; a page of linkage held as a subset both ways; a link to another origin never requested and noted; a 503 not decided; the SHOULD's skip when no relationship carries linkage; and the budget, at exactly 200 requests over 250 articles (750 links). For the top-level `self`: a pass, a `self` with a query costing one request and one equal to the URL fetched costing none; an answer that is no resource data (no `data`, a string, an item without `type`) failing the MUST; a different resource, which the MUST passes and the SHOULD fails; a collection's `self` answering a single resource; a 404; `null` answering a resource; a whole collection compared in any order, missing one and adding one; a page (the answer's `next`, or the carrying document's `prev`) held only to answering a collection, and failed when it does not; a link to another origin never requested and noted; a link that is not a link; a 503 not decided; the skip naming what it searched; a relationship endpoint's top-level `self` followed and held to the same linkage; and the budget over 201 read endpoints. Every link the MUST of a pair fails, the SHOULD leaves not decided, naming it. Against an api declaring no read endpoint, each rule's skip names the endpoints it searches. `skip: ["spec/links/"]` is pinned to leave all seven out. An in-process case holds the real router to the rule, including a link to a path no route serves, which fails it rather than killing it; `src/internal/conformance/core.test.ts` pins that only `RouteNotFound` is answered so, any other router failure dying.

**`skip` and `requestTimeout` are pinned at both ends** ([#302](https://github.com/thomasfosterau/effect-jsonapi/issues/302)). `Conformance.test.ts` asserts that `skip` leaves out exactly the rules its prefixes match (the pagination walk, the link crawl and a section among them), adding no `Skipped` outcome; that it removes rules from what `only` and `tiers` select; and that a rule both `only` and `skip` name is left out. Against a canned server that never answers, a run with a 10ms `requestTimeout` finishes, interrupts every request it sent, and reports exactly what a transport that fails at once reports, but for the note naming the timeout; against the conformant server, a timeout no request reaches changes no outcome, through a client's `retry` too. `core.test.ts` pins the runner under the test clock: a request is still pending a millisecond before the timeout and a lost response naming it at the timeout, with no redirect recorded; a body held open is cut short too; each redirect hop has a timeout of its own (two 600ms hops pass under a one-second timeout, and a hop that never answers is cut short a second after it is requested, counting as a request sent); a client's own `retry` runs within the timeout (a first attempt that hangs is cut short with the run's one request, and the second attempt, which would answer, is never made); and with the timeout turned off (`"Infinity"`) the runner waits as long as the transport does. The default is pinned twice: `core.test.ts` holds `requestTimeoutOf` to thirty seconds when unset, no timeout for `"Infinity"` and `Duration.infinity`, and a defect for zero, a negative duration, `NaN` and a duration `Duration` cannot read (`"1e3 seconds"`), and the runner to a request still pending a millisecond before thirty seconds; `Conformance.test.ts` holds a run that sets nothing to cutting each request short at thirty seconds under the test clock, through `verifyWith` and in process through `verify` alike (handlers that never answer, still waiting a millisecond before), a run that turns it off to still waiting an hour later, and a run with a non-positive or unreadable timeout to dying before it sends a request, against a client that answers at once, so a run that sent one first would finish and be caught rather than hang.

## 10. Open questions

- **Is `cleanup` required?** The write fixture ([#162](https://github.com/thomasfosterau/effect-jsonapi/issues/162)) ships it **optional** — the less demanding contract — so an in-process target known to be disposable can omit it, and the kit reports what it left (§1.4). The alternative is to require `cleanup` whenever `create` is given, which makes a live-server run safe by construction at the cost of a no-op cleanup in every in-process test. An owner decision.
- **Machine-readable output.** `format` renders text. A JSON rendering of `Report` is trivially derivable (it is plain data) but no stable serialisation is committed to yet.
- **A default `requestTimeout`** — answered: thirty seconds, for `verify` and `verifyWith` alike, overridable and with `"Infinity"` to turn it off (§1.5; owner decision on [#302](https://github.com/thomasfosterau/effect-jsonapi/issues/302#issuecomment-6186007738)). The cost it accepts is that an endpoint slower than that reads as a lost response; a run against one sets a longer timeout.
- **How a top-level `self` of a collection is compared** — answered ([#309](https://github.com/thomasfosterau/effect-jsonapi/issues/309#issuecomment-6190325231), 2026-10-15): the rule splits, as the `related` link's did. `top-level-self-dereferences` (MUST) holds the link to answering resource data; `top-level-self-matches-document` (SHOULD) holds it to a document of the same kind, comparing a collection resource for resource, in any order, only when neither document carries `next` or `prev` (§3). A relationship's `self` splits the same way, the MUST holding the answer's shape and cardinality and the SHOULD its identifiers.
- **A link the same run just received that answers 404.** The link rules ([#168](https://github.com/thomasfosterau/effect-jsonapi/issues/168)) report it as a finding, and leave a `401` / `403` not decided. #168 left this to be decided; the alternative is to treat a 404 as not decided too, which would excuse exactly the drift (a moved route) the rules exist to catch. An owner decision.
- **Sampling the link crawl.** Each link rule makes at most 200 requests per run and skips when that is not enough, so a server whose read endpoints answer large collections by default gets these rules skipped rather than sampled. [#302](https://github.com/thomasfosterau/effect-jsonapi/issues/302) settled the cost question with `skip` and `requestTimeout` (§1.5) and no per-rule budget option; sampling some links per endpoint remains possible later.
- **Rule versioning.** Rule ids are the stable surface a consumer pins against; a policy for renaming or retiring one is not yet written.
