# Conformance kit

The table above is what the constructors guarantee. It says nothing about your server once a handler has an opinion — so `Conformance` is an **executable specification** you run against your own `HttpApi`, which fails naming the broken rule and citing its section rather than printing an assertion diff.

```ts
import { Effect } from "effect";
import { Conformance } from "@thomasfosterau/effect-jsonapi";
import { Api } from "./api.js";
import { BlogLive } from "./handlers.js";

const report = await Effect.runPromise(
  Conformance.verify(Api, {
    // the fixture contract: one known-existing id per resource type
    ids: { articles: "1", people: "9" },
  }).pipe(Effect.provide(BlogLive), Effect.scoped),
);

console.log(Conformance.format(report));
```

Endpoints are discovered from the `HttpApi` value — method, path, declared query families, response media type — but every rule is decided by a real request/response pair, because conformance is a wire property and the typed client both hides the raw status, media type parameters and unparsed body, and refuses to construct the malformed requests half the rules need to send. `verify` drives an in-memory transport over the real router (no port bound, no fixture beyond the ids); `Conformance.verifyWith(api, { client, baseUrl })` runs the **identical** rules against a deployed server over `FetchHttpClient`.

Failures read as a report, not a diff:

```
FAIL  spec/content-negotiation/accept-weight-is-not-a-parameter
      MUST NOT · Content Negotiation (with RFC 9110 §12.4.2)
      A `q` weight is an Accept-header parameter, not a media type parameter (RFC 9110 §12.4.2),
      so a JSON:API media type instance carrying only a non-zero `q` MUST NOT be counted as
      parameterised and MUST NOT be rejected with 406.
      https://jsonapi.org/format/1.1/#content-negotiation-servers
      · a weighted preference between HTML and JSON:API was treated as a disallowed media type parameter
        GET /articles/1  [accept: text/html;q=0.9, application/vnd.api+json;q=0.8]
        expected: any status but 406 — the weight is not a media type parameter
        observed: 406 application/vnd.api+json — {"errors":[{"status":"406", …
```

**Writes need a fixture, and are opt-in.** The kit cannot invent a payload your server will accept, so the create / update / delete rules (201 with the created resource, `Location`, the update and delete responses, the atomic extension's response media type, `lid` resolution, all-or-nothing processing and the order of `atomic:results`) run only with `mutating: true` and a write fixture per type:

```ts
let n = 0;
Conformance.verify(Api, {
  ids: { articles: "1" },
  mutating: true,
  writes: {
    articles: {
      create: () => ({
        type: "articles",
        attributes: { title: `conformance probe ${++n}`, body: "…" },
        relationships: { author: { data: { type: "people", id: "9" } } },
      }),
      update: () => ({ attributes: { title: `conformance probe ${++n} (updated)` } }),
      cleanup: (id) => deleteArticleFromYourStore(id), // an Effect
    },
  },
});
```

Each write rule creates its own target from `create`, and acts on the id the server's create response named only after checking it: the response must name a resource of the type `create` returned, under an id that is a URL path segment of its own (not `""`, `.`, `..` or a lone surrogate) and is neither an `ids` sample, nor one a read earlier in the run returned (unless the kit had already taken it from a create of its own), nor one the run already holds — anything else is recorded as named and never updated, deleted or passed to `cleanup`. That check refuses only ids that are evidently not what the kit created: a server that answers a create with the id of some other existing resource cannot be told from an honest one, so run `writes` only against a server and data you can afford to have modified. `cleanup` runs after the rule that made it whether that rule passed, failed or died; and `report.writes` (printed under `WRITES`) lists everything the run created and what became of it. A type with no fixture skips its write rules naming the missing key. The client-generated id rules (201 or 204 under a client id, the 409 for a duplicate one, or 403 where they are unsupported — and the same of an atomic `add` under one, where the api has an operations endpoint) run only for a type whose fixture adds `clientId: { supported, id }` — the kit never makes up an id — and the relationship mutation rules (`PATCH` / `POST` / `DELETE` on `/relationships/…`, read back through the relationship's `GET` — a to-one `PATCH` of `null` included — what each answers, and the 404 for linking `absentId`) link a created resource to the `ids` sample of the related type. `cleanup` may be omitted for a target you throw away (an in-process store) — the report then lists what was left — but supply it against anything that outlives the run.

Two tiers, separately runnable. `spec` is JSON:API v1.1 alone; `profile` is this package's filter grammar profile, the Idempotency-Key profile's advertisement (with the write fixture, a create or an update on an endpoint declaring `Idempotency-Key` must name the profile in `jsonapi.profile` — answer with `jsonapi: Idempotency.jsonapi` — or on its media type) and the conventions it adds where the spec declines to have one. Pass `tiers: ["spec"]` to hold a server to the specification without adopting any of this library's opinions.

**It says what it did not check.** Every rule that could not run reports why — no endpoint of that shape, no sample id, no write fixture, a mutating probe not opted into — and `Conformance.gaps` declares the areas the kit does not cover at all (filter _evaluation_ semantics beyond what the sample shows, retried writes under the Idempotency-Key profile, concerns outside JSON:API), each with its reason and tracking issue. Both are printed in every report, and skips are counted separately from passes, so a run that proved little cannot read as a clean bill of health.

**A rule that dies does not cost you the report.** A defect in one rule — a transport that throws, or a bug in the kit — becomes that rule's `Errored` outcome (printed as `DIED`, with the defect's message, and counted as `errored` by `Conformance.summarise`); every other rule still runs and is reported, and so is `report.writes`. Interruption is not caught: it still stops the run, after the cleanup of whatever the interrupted rule created. A write fixture member that throws is not a defect, whatever it throws: a `create` or `update` that throws skips the rules it would have driven, and a `cleanup` that fails or throws is recorded in `report.writes`.

Use `Conformance.assert(report)` as a gate: it fails with a `ContractViolation` carrying the rule, its requirement, its citation and the request that decided it. A rule that died is not a finding about your server, but the run could not decide it either, so `assert` dies on it — with a defect tagged `RuleDied` naming the rule and the defect, the original as its `cause` — rather than passing. If you gate on `summarise(report).failed` or `findings(report)` instead of `assert`, also check `summarise(report).errored === 0`.

**Against a live server, bound the run.** `verifyWith` runs the identical rules over any `HttpClient` and `baseUrl`. Two options bound what that costs the server:

- `skip` — rule-id prefixes to leave out, the complement of `only` and matched the same way, by path segment: an entry matches the rule with that id and every rule whose id continues it with `/`, so `skip: ["spec/status/create-location"]` leaves out that rule alone, keeping `spec/status/create-location-matches-self`, and a partial segment (`"spec/content-neg"`) matches nothing. `skip: ["spec/pagination/links-enumerate-collection", "spec/links/"]` leaves out the pagination walk and the link crawl, the rules that make the most requests. It removes rules from what `tiers` and `only` select, and a rule it leaves out is absent from the report, as one `only` does not select is.
- `requestTimeout` — a `Duration.Input` (`"10 seconds"`) bounding each request, its body included; each redirect hop gets its own. A request still unanswered then is aborted and reads as a lost response naming the timeout, which every rule treats as any transport error. Thirty seconds by default, for `verify` and `verifyWith` alike; `requestTimeout: "Infinity"` (or `Duration.infinity`) turns it off, so the kit waits as long as the transport does. A duration that is not positive, or one `Duration` cannot read (e.g. `"1e3 seconds"`), is a defect.

## Design

### What is under test

**A transport, discovered from an `HttpApi` value.**

Two things are deliberately separated:

- **Discovery is static.** `Conformance.verify` walks `api.groups[*].endpoints[*]` and reads each endpoint's method, path, path parameters, flat wire query keys (`include`, `sort`, `fields[articles]`, `page[limit]`, and whether `filter[…]` is an index signature — i.e. the grammar — or named keys — i.e. the escape hatch) and its declared response media type. The query keys are read by the same walk `Middleware.SchemaErrors` checks requests against, so a hand-built query that is a union declares what any member declares and a suspended one what its target declares; a query that could accept a name the walk cannot enumerate — a record keyed by any string, say — is recorded as such, as the middleware stands aside for it. From the method and the path's segment shape it assigns a **role**: `collection`, `resource`, `create`, `update`, `delete`, `related`, `relationship`, `relationshipWrite`, `operations`. Nothing is requested during discovery, so the report can name both the endpoints it probed and the ones it could not build a URL for.
- **Observation is wire-level.** Every rule is decided by a real request/response pair.

#### Why not the typed client

`HttpApiTest.groups` returns an `HttpApiClient`, which is the wrong instrument here for two reasons:

1. **It hides what has to be checked.** Conformance is a wire property — the raw status code, the media type's _parameters_, the unparsed body, whether `included` carries a duplicate. The typed client decodes all of that away.
2. **It cannot express the probes.** Half the rules send deliberately malformed requests: a `Content-Type` with a `charset` parameter, an `Accept` whose every JSON:API instance is parameterised, `?fields[articles]=` naming a field that is not there, `?unknown=1`, a repeated `filter[…]` key. A typed client refuses to construct them, which is exactly its job and exactly why it is not the seam.

So the kit builds an in-memory `HttpClient` over the real router — the same `HttpRouter.toHttpEffect` + `HttpClient.make` technique `HttpApiTest` uses, stopping one step earlier — and drives raw requests through it.

#### In-process _and_ over the wire

This is not an either/or, and it should not be two kits.

|  | `Conformance.verify` | `Conformance.verifyWith` |
| --- | --- | --- |
| Transport | in-memory over the real router | any `HttpClient` you pass |
| Binds a port | no | n/a (whatever you point it at) |
| Handlers | from the ambient context, as `HttpApiTest` takes them | the deployed server's |
| Rules | **identical** | **identical** |

In-process is the default because it is deterministic, fast (~100–200 requests in well under a second) and needs no fixture beyond sample ids. It still exercises request decoding, routing, middleware, the handler and response encoding — the whole pipeline the rules care about. A request no route serves — which a link the server emitted can lead to — is answered as a deployed server answers it (`HttpServerError.causeResponse` on the router's `RouteNotFound`: an empty 404), not turned into a defect that would make the rule that sent it `Errored`. Only `RouteNotFound` is answered so: any other failure of the router, like any defect, still dies, as a transport that throws does, because what a deployed server would answer to it is not known. `verifyWith` takes `FetchHttpClient` and runs the same rules against a deployed server, for the things only a real deployment has: a reverse proxy rewriting `Content-Type`, a CDN, a gateway that normalises headers.

**A redirect is followed only within the base URL's origin**. The transport itself follows nothing: over the wire the kit provides `FetchHttpClient.RequestInit` with `redirect: "manual"` for its own requests, set over the rest of the `RequestInit` the run's context holds, so a run's own `redirect: "follow"` cannot undo it. The kit then follows a redirect itself, in both transports, after checking where its `Location` leads: only to the base URL's origin — scheme, host and port, so an `http` → `https` redirect on the same host is to another origin — and so, unless the client follows redirects itself (below), no request is ever sent to another origin on a server's say-so. A `301`, `302` or `303` is followed only for a `GET`, since `fetch` would turn any other method into a `GET`; a `307` or `308` re-sends the same method and body. At most five hops are followed for one request, each a request of its own that counts against a rule's request budget, and the final answer is what the rule grades. A `3xx` with no `Location`, or an empty one, answers as itself. A redirect the kit does not follow — to another origin, past the cap or the budget, turning a write into a `GET`, or to a `Location` that does not parse — leaves the request with no answer to read, and so does one a transport followed on its own to another origin or turning the method into a `GET` (below). A rule that sent such a request — a probe, a read endpoint a link rule searches, a link it follows, a page of a pagination walk — drops a finding the request produced, so a probe that was never answered is never reported "not rejected", while a finding on an answer the kit did read still fails the rule. Otherwise the rule is `Skipped`, naming the redirects — the first three by their request and `Location`, the rest counted — and keeping the rule's own note; a rule that skipped on its own keeps its reason, with the redirects named after it. There is never a partial pass on the answers it did read, and no rule opts out, the link rules and the pagination walk included. `spec/target/reachable` alone decides for itself: a read endpoint that answers with a redirect the kit does not follow is a finding there, telling the caller what to change — point `baseUrl` at the URL that serves; for a chain on the base URL's origin past the hop cap, shorten the chain; for a `Location` that does not parse, fix it on the server; for a redirect the transport followed itself, pass a client that does not. A client that rewrites every request onto another origin (`HttpClient.mapRequest` mapping a `baseUrl` of `http://api.invalid` onto a local port, say) follows nothing, and is read as the server it sends to. The kit runs each request through the client as the client's own `execute` does — its postprocessing, where `HttpClient.followRedirects` follows and `HttpClient.retry` retries, over its preprocessing, where `HttpClient.mapRequest` rewrites — and takes the request the preprocessing last produced as the one the client sent: its origin is where a redirect the transport followed is judged from (below), and a `Location` on that origin, absolute or not, is followed as one on the base URL's, the kit requesting the path it names through the client again. A client that rewrites the path as well (adding a prefix, say) adds it again to the path a followed hop names, exactly as it does to a relative `Location`'s. A preprocessing that fails sends nothing, and is read as a transport error, unless the client's own `retry` recovers from it. Two limits remain. A transport that follows redirects on its own, outside `fetch`'s `RequestInit` (one wrapped in `HttpClient.followRedirects`, say), still sends the request. The kit then refuses to read what the transport ended with — an answer, or a transport error such as a refused connection — when the request behind it is on another origin than the one the client sent, or carries another method (a `301` or `302` turns a `POST`, a `303` any method but `GET`, into a `GET`), and records the request as answered by a redirect it did not follow, naming the URL the transport ended at, so the rule that sent it is held to the same rule as any other redirect the kit does not follow: never a "not rejected", never a partial pass. Only that final URL and method are checked: a chain the transport followed off the origin and back (A → B → A), keeping the method, is read as an answer from A, undetected. And the request has been made either way, so hand `verifyWith` a client that does not follow redirects. And a `RequestInit` given only to the client's own layer (`FetchHttpClient.layer.pipe(Layer.provide(…))`) is replaced for the kit's requests, since the kit's takes precedence there; provide it to the run instead.

#### The fixture contract

Deliberately the smallest one that works:

```ts
Conformance.verify(api, {
  ids: { articles: "1", people: "9" }, // one known-existing id per resource type
  paths: { "search.search": "/search?filter[q]=x" }, // an explicit URL where the convention can't reach
});
```

`ids` is keyed by resource type, which under the conventional paths is the first literal path segment. A rule that cannot resolve a URL reports **`Skipped`, naming the option it wanted** — never a pass:

```
SKIP  spec/document/top-level-members
      not checked: no sample id for "articles" — pass ids["articles"] or paths["articles.get"]
```

A rule that probed _some_ endpoints but not others passes with a note saying how many it never reached, so partial coverage never reads as full coverage.

**A sample the server does not hold fails no rule**, but every rule that reads it sees less of the api than the run suggests. So `Report.samples` records every `/:type/:id` read the `ids` resolve — `{ type, id, url, status }`, in discovery order — with the status the run's first plain read of that URL answered (a `GET` with the JSON:API `Accept`, no query; `0` for no answer). A sample no selected rule read is left out rather than read for the purpose, so a run narrowed by `only` / `skip` / `tiers` sends only its rules' requests; a full run reads every one. `format` names the non-2xx ones under `SAMPLES`, and prints nothing there when every sample resolved. An unresolved sample is not a gap, is not counted by `summarise` (which counts outcomes, as it does not count `writes`) and does not fail `assert`; a fixture test asserts on `report.samples` instead of matching a note's wording.

#### The write fixture

`ids` cannot drive a write: the kit cannot synthesise a payload a server will accept (attributes carry domain constraints, required to-one relationships point at resources that must already exist, and a payload rejected with a 422 proves nothing about the 201 rules), and it cannot undo what it created. So the write rules take a second, opt-in contract, keyed by resource type like `ids`:

```ts
Conformance.verify(api, {
  ids: { articles: "1" },
  mutating: true, // the master switch: nothing writes without it
  writes: {
    articles: {
      // a payload the server will accept, in wire form — called once per create
      create: () => ({
        type: "articles",
        attributes: { title: `conformance probe ${++n}`, body: "…" },
        relationships: { author: { data: { type: "people", id: "9" } } },
      }),
      // a PATCH that must succeed against a resource `create` made; the kit adds type and id
      update: () => ({ attributes: { title: `conformance probe ${++n} (updated)` } }),
      // removes a resource the kit created, by the id the server assigned
      cleanup: (id) => Effect.sync(() => store.delete(id)),
      // opt in to the client-generated id rules: whether the server supports
      // them, and an id to send — the kit never makes one up
      clientId: { supported: false, id: () => `conformance-client-${++n}` },
    },
  },
});
```

What the kit promises in return:

- **It refuses an id it evidently did not create.** Every write rule creates its own disposable target from `create` — the update rule PATCHes it, the delete rule DELETEs it — and acts on the id the server's create response named only after checking it: the response must name a resource of the type `create` returned (`data.type`, or for an `add` the `data.type` of the `atomic:results` entry at that operation's position), under an id that is a URL path segment of its own (not `""`, `.` or `..`, which `encodeURIComponent` leaves alone and URL normalisation turns into the collection or `/`, nor a lone surrogate, which no URL can carry), that is not an `ids` sample, that no successful `GET` earlier in the run returned (as primary data, in `included`, or as a relationship's linkage) while the kit held no live resource under it — a read-back of the kit's own resource, made before it was removed, is not counted, but a sighting of the same id after the kit removed its resource is another holder's and is — and that the run does not already hold a resource for that has not been removed (two live resources cannot share an id, so one of the two answers is wrong). Any other id is recorded as `left`, with `detail` naming what was named — "named `people:1`, which the kit did not create … — not touched" — and is never PATCHed, DELETEd or handed to `cleanup`; the rules that would have acted on it skip, saying so. An id the server hands out again once the kit has removed its first holder — a `size + 1` store, a SQLite rowid — is accepted, because refusing it would leave every later resource behind. (Before the fixture, `mutating: true` made the delete rule delete the `ids` sample.) Every rule that creates nothing (the profile tier's included) runs before the first rule that creates, so a create is checked against everything the run reads; the report keeps the suite's order. The read check can refuse falsely: linkage can name a resource since deleted, and a server that reuses ids may hand that id to the kit's create. That fails safe — the resource is recorded as `left` with a `detail` saying why, and the rules that would have acted on it skip.
- **Cleanup runs however the rule ends.** Each target is created inside `Effect.acquireUseRelease`, so `cleanup` runs after the rule that made it whether that rule passed, failed or died. A cleanup that fails or throws is recorded as `cleanup-failed`, not propagated, so one bad cleanup cannot cost the run its report — whatever it fails with: `detail` renders the value as a rule's defect message is, and a value the kit cannot read at all (a revoked `Proxy`, say) as `[unrenderable defect]`.
- **The run is auditable.** `Report.writes` lists every resource the kit created, the rule that created it and what became of it — `deleted` by the kit's own DELETE (or by an atomic `remove` in the request that created it, confirmed by a read that no longer finds it), `cleaned-up`, `cleanup-failed` with the cause, or `left`. `format` prints them under `WRITES`, with the count still in place.
- **Each sub-key gates only its own rules.** A type with no `create` skips every write rule naming `writes["<type>"].create`, exactly as a missing `ids` entry does; a create-only type omits `update` and skips only the update rule. Never a vacuous pass.
- **A key goes only where one is required.** A write to an endpoint declared `idempotency: "required"` carries a fresh `Idempotency-Key`, so that endpoint does not refuse it with a 400; a key never sent before can only be a first attempt, never a replay. That holds for every write the kit sends: the creates, updates and deletes through resource endpoints, and both requests to the atomic operations endpoint (the `add`, and the malformed document `malformed-operations-rejected` sends, so its 4xx is about the document, not a missing key). An endpoint where the key is optional gets none, and processes the write normally. The kit reads the header as required from a headers struct whose own property for it is not optional, or from a union every member of which (read through a suspended schema to its target) requires it so; one where any member declares it optionally or not at all reads as optional. An endpoint that requires it some other way the kit cannot see — a refinement or a middleware insisting on a header the schema leaves optional, say — reads as optional and gets no key, and may refuse the write for that alone. So a request sent without a key, to an endpoint declaring the header, may draw a refusal whose error document names `source.header: idempotency-key`, and the two rules that can meet one read it differently. `delete-response` judges the answer itself: only a `400` naming the header — the package's own missing-key `400` (`docs/idempotency.md` §2) — decides nothing, and any other refusal fails, a `409` or `422` naming the header included, since the package's `KeyInProgress` and `KeyMismatch` are no answer to a delete without a key. `malformed-operations-rejected` judges only whether the server examined the document, and a refusal over the key says nothing about that, so any 4xx naming the header leaves it not decided rather than passing on it.
- **The kit never makes up a client-generated id**. The client-generated id rules run only for a type whose fixture opts in with `clientId`, and only for the case it declares: `supported: true` runs `create-client-id` and `create-conflict-id`, `supported: false` runs `create-client-id-unsupported` — and, where the api declares an atomic operations endpoint, their `add` counterparts `spec/atomic/add-client-id`, `add-conflict-id` and `add-client-id-unsupported`; the others skip, saying which case the fixture declares. Each create sends `clientId.id()` as `data.id` beside `create`'s payload, and what it makes is vetted, recorded and cleaned up as any other create's — a 204 names no id, so the kit takes the one it sent. An atomic probe sends one `add` per request, carrying the id as `data.id`; an `add` result with no `data` names no id either, so the kit takes the one it sent. Without `clientId` every one of them skips naming `writes["<type>"].clientId`.
- **The relationship mutation rules link to an `ids` sample.** They need no fixture member of their own: each creates a resource from `create`, links it to the `ids` sample of a type the relationship write endpoint's payload names (discovery reads the identifiers' `type` literals off the payload schema), and reads the linkage back. The sample is only linked to, never written to — but a server that stores the inverse side on it (a comment's one article, say) changes it, so give such a type a sample you can afford to have relinked. Without a sample for any type the payload names, the endpoint skips naming `ids["<type>"]` — except for the 404 probe, which links `absentId` under the first type the payload names, and needs no sample.
- **A rejected payload is not a verdict.** If the server does not accept `create` (a 4xx, say), the rules it was for report `Skipped` with the status and body — the fixture is wrong or the server is, and the kit cannot tell which.

Four edges of the contract, stated so nobody relies on the opposite:

- **The kit cannot tell a lying server from an honest one.** It refuses only an id that is evidently not what it created — the wrong type, an `ids` sample, one a read returned, a live duplicate, an unsafe path segment. Any other id is trusted, so a server that answers a create with the id of an existing resource the run never saw has the kit update, delete and `cleanup` that resource. Run `writes` only against a server, and data, you can afford to have modified.
- **A non-2xx create is taken to have created nothing.** Nothing is recorded for it and nothing is cleaned up. A server that creates and then answers an error leaves that resource behind, unreported.
- **`cleanup` runs uninterruptibly.** It is the release step of `acquireUseRelease`, so a `cleanup` that never completes hangs the run; give one that talks to a remote store its own timeout.
- **`cleanup` requires no services** (its `R` is `never`): close over, or provide, whatever it needs before handing it to the kit.

**`cleanup` is optional.** Against a target known to be disposable — an in-process store the test throws away — it can be omitted; the kit then leaves what it created in place and says so (`left`, naming `writes["<type>"].cleanup`). Against a server whose state outlives the run, always supply it.

#### Against a live server: `skip` and `requestTimeout`

Two options bound what a run costs a server whose state and uptime matter: which rules run, and how long the kit waits for an answer.

```ts
Conformance.verifyWith(api, {
  client,
  baseUrl: "https://api.example.com",
  ids: { articles: "1" },
  requestTimeout: "10 seconds", // any Duration.Input; thirty seconds when unset
  skip: ["spec/pagination/links-enumerate-collection", "spec/links/"],
});
```

**`skip` leaves rules out by id prefix — the complement of `only`.** A prefix is matched exactly as `only` matches one, by path segment: it matches the rule whose id it is, and every rule whose id continues it with `/`. So `"spec/links/"` (or `"spec/links"`) leaves out the seven link rules (the link crawl, §3) and `"spec/pagination/links-enumerate-collection"` the pagination walk, the kit's most expensive rules against a live server. The three selections compose in one order: `tiers` and `only` select, and `skip` removes from what they selected, so a rule both `only` and `skip` name is left out. A rule `skip` leaves out is absent from the report, exactly as one `only` does not select is: the report lists what the run tried, and a `Skipped` outcome means a rule that ran and could not decide (§4.1), not one the caller declined to run. A prefix that matches nothing leaves nothing out, as one in `only` selects nothing. A prefix never reaches past the end of a segment: `"spec/status/create-location"` matches that rule alone, not `spec/status/create-location-matches-self`, and a partial segment such as `"spec/content-neg"` matches nothing, in `only` and `skip` alike.

**What a run leaves out narrows what the write rules vet a create against.** A create is refused when it names an id a successful `GET` earlier in the run has shown (`Context.observed`, §1.4), a check only as complete as the reads before it — so a read rule `skip` or `only` leaves out, or a read `requestTimeout` cuts short, is a read that check does not see.

**`requestTimeout` bounds each request in time.** A request still unanswered when it runs out is interrupted (over `fetch`, aborted) and reads as a lost response: status `0`, with a transport error naming the timeout (``no response (no answer within 30s, the run's `requestTimeout`)``). Every rule treats it exactly as it treats a refused connection or a reset — `spec/target/reachable` reports it, the pagination walk and the link crawl leave what it cut short not decided — and never as a redirect the kit did not follow, so the [#333](https://github.com/thomasfosterau/effect-jsonapi/pull/333#issuecomment-6181006987) rule that a request a redirect left unanswered skips the rule that sent it does not apply. It bounds one request: the client's whole `execute`, a `retry` the client wraps itself in included (the kit still runs each request through the client exactly as its `execute` does, §1.2), and the reading of the answer's body, so a server that sends its headers and holds the body open is cut short too. Each redirect hop the kit follows is a request of its own, with a timeout of its own and counting against the rule's budget as before, so one probe waits at most six timeouts (the first request and five hops). A request it cuts short was still sent, and still counts against the budget. A create it cuts short is taken to have created nothing, as a non-2xx one is: the server may have created it all the same. It does not bound `cleanup`, which is not a request the kit sends.

**It defaults to thirty seconds**, for `verify` and `verifyWith` alike, so a server that holds a response open costs a run at most that per request, and a run that sets nothing is bounded too. Any positive `Duration.Input` overrides it. `requestTimeout: "Infinity"` (or `Duration.infinity`, the same value) turns it off: the kit then waits as long as the transport does, as it did before the option existed, so a server that holds a response open holds the run. `"Infinity"` is the spelling because it is already a `Duration.Input`, so the option keeps one type and needs no second sentinel. A duration that is not positive — zero, a negative one, or `NaN`, which `Duration` reads as zero — would cut every request short before it was answered, so it is a defect in the options, as is one `Duration` cannot read (e.g. `"1e3 seconds"`): the run dies before it sends a request, rather than reporting every rule undecided.

### Two tiers, separately runnable

| Tier | What it is | Authority |
| --- | --- | --- |
| `spec` | JSON:API v1.1 alone | `https://jsonapi.org/format/1.1/` and the atomic extension |
| `profile` | this package's own profiles — the filter grammar and the Idempotency-Key profile — and the conventions it takes a position on where the spec declines to | `docs/filter-grammar.md`, `docs/idempotency.md`, the README |

`tiers: ["spec"]` runs the first without the second, so a consumer can hold themselves to the specification without adopting anything of this library's. A test asserts that no profile rule ever cites `jsonapi.org/format` as its authority.

### What v1 covers

84 rules. Every one carries a stable id, an RFC 2119 level, a section and a URL.

**Content negotiation (§Content Negotiation, §Extensions, §Profiles)** — the response media type and its permitted parameters; 415 on a parameterised request `Content-Type` (probed without `mutating: true`, so it sends the create endpoint — or failing that an update or relationship endpoint — a body `{}` that nothing can apply); 406 when every `Accept` instance is parameterised; an unsupported `ext` URI; an unrecognised `profile` ignored rather than rejected; and the two RFC 9110 §12.4.2 weight rules — a non-zero `q` is not a media type parameter, `q=0` is a refusal. The kit reported the first of those against the shipped middleware before [#101](https://github.com/thomasfosterau/effect-jsonapi/issues/101) was fixed; it now guards the fix against regressing.

**Document structure (§Document Structure, §Compound Documents, §Resource Objects)** — at least one of `data` / `errors` / `meta`; `data` and `errors` never together; `included` only alongside `data`; full linkage, computed transitively from the primary data through included resources' linkage — starting from the primary identifiers themselves when the primary data is resource linkage, as a relationship document's is, and waived as the spec waives it "when relationship fields that would otherwise contain linkage data are excluded due to sparse fieldsets": the wire cannot show what an excluded relationship linked, so once the walk reaches a resource of a type the probe's `fields[TYPE]` names, no member is reported ([#494](https://github.com/thomasfosterau/effect-jsonapi/issues/494); `Middleware.SchemaErrorsLive` makes the same walk on every encoded success); no duplicate `(type, id)` among the document's resource objects, which leaves out a relationship document's primary identifiers, so the full resource for one may sit in `included`; an `included` array, `[]` when nothing is included, in every 2xx answer to a request carrying `include` (`spec/document/included-on-include`, §Fetching Includes); `type` and `id` present and strings; the `jsonapi` object's member types.

The document rules probe **compound** documents, not just bare ones: for each endpoint declaring `include`, the kit reads the includable relationship names off a baseline response (only those carrying inline `data` — a paginated relationship is links-only and including it is a legitimate 400) and re-probes with them. A relationship endpoint declaring `include` is re-probed with its own relationship's name instead (`GET /articles/1/relationships/tags?include=tags`), since its primary data is identifiers that carry no relationships to read. That holds for a paginated relationship too, whose own name is legal on its own relationship endpoint and brings in the resources on the page answered (`GET /articles/1/relationships/comments?include=comments` in the blog). Without that, full linkage and duplicate detection would pass over documents that never carry `included`, which is a pass that proves nothing. `spec/document/included-on-include` reads those compound probes and sends one more to every endpoint declaring `include`: a bare `?include=`, which supplies `include` but asks for nothing, so its `included` must be the empty array. Presence is the signal — an `include` with an empty value is still supplied — and a response to a request without `include` is never checked for the key. The rule reports `Skipped` when no such request drew a 2xx.

**Error objects (§Errors, §Error Objects)** — the `{ errors: [...] }` shape; member types; `source` discrimination (`pointer` / `parameter` / `header` only, `pointer` a real JSON Pointer); and `status` agreeing with the response status.

**Query parameters (§Sparse Fieldsets, §Inclusion, §Sorting, §Query Parameters)** — sparse fieldsets applying to primary data _and_ to `included` (two rules, because they fail independently), the `included` one taking its compound baseline from a relationship endpoint as the compound probe does, with `?include=` of its own relationship, while the primary one has nothing to judge there, a relationship document's primary data being identifiers; an empty `fields[TYPE]=` answered with no fields, not every field (`spec/query/sparse-fieldsets-empty`, [#488](https://github.com/thomasfosterau/effect-jsonapi/issues/488): "An empty value indicates that no fields should be returned"), probed on each endpoint declaring `fields[TYPE]` for every type its baseline answered with a field — all three judged on `attributes` and `relationships` alike, a resource's fields together (§Resource Object Fields), so an unrequested relationship is as much a finding as an unrequested attribute, and the field a projection probe requests is the first one the baseline shows, an attribute where there is one; an unidentifiable `include` path is a 400; an unsupported `sort` field is a 400; and an all-lowercase unrecognised query parameter is a 400, as are, since a parameter whose base name is not a legal member name and one of an extension the server does not support (the two rows at the foot of the table below, which, like that rule, probe the first read endpoint whose baseline response is 2xx and are decided as the refusal rules below are, `source.parameter` and all, since guarding the 400 [#263](https://github.com/thomasfosterau/effect-jsonapi/issues/263) added to the middleware). Those `include` / `sort` rules probe an endpoint that declares the family; two more probe one that does not, guarding the 400 [#261](https://github.com/thomasfosterau/effect-jsonapi/issues/261) added to the middleware, and seven more send a parameter of a family the specification defines that the endpoint does not declare: a `fields[TYPE]`, `page[…]` or `filter[…]` the endpoint does not support at all, an undeclared member beside the `page` / `filter` members it does declare, and a bracketed `include[]` / `sort[]` beside the bare parameter it supports:

Whether an endpoint declares the family is read from discovery (its flat wire query keys), not from a new option. A status other than 400 is a finding. So is a 400 whose error objects carry `source.parameter` naming only other parameters, since that 400 refused something else; a 400 naming no `source.parameter` at all passes with a note saying the status alone decided it, because JSON:API makes `source` optional ("It **SHOULD** include one of the following members or be omitted"); the note says whether the 400 carried error objects without `source.parameter` or no JSON:API error objects at all. A server error (5xx) is a finding too: a server that answers 5xx to a parameter it does not support mishandled it. A rate limit (`429`), a request timeout (`408`) or no response at all (a lost one, or one `requestTimeout` cut short) says nothing of whether the server refuses the parameter, so every refusal rule — the two of #278, the seven of #310 and the three parameter-name rules alike — leaves such a probe not decided, skipped, naming what answered. The link and pagination rules draw that line elsewhere: they decide nothing on a server error either. Each refusal rule sends at most 20 requests, the redirects it follows included — a baseline per endpoint it tries and the one probe — and skips, naming the endpoints it passed over, when that budget runs out before a usable endpoint. The seven read what an endpoint declares by the check `Middleware.SchemaErrors` runs (`declaresName`, over the endpoint's flat wire keys and its open family prefixes), so none sends a name the endpoint declares. Discovery counts a name the endpoint declares with no legal value (a `fields[TYPE]` whose type has no attribute, say) as declared, though the middleware refuses it: the kit then does not probe it, the side on which it can only miss a 400, never demand one the middleware would not give. An endpoint whose query names discovery cannot enumerate (§1) is never probed, since whether it declares the family is unknown. The three parameter-name rules (`spec/query/unknown-query-parameter`, `spec/query/illegal-parameter-name`, `spec/query/unsupported-extension-parameter`) are the exception: no endpoint can declare a name the specification forbids, so every read endpoint is a candidate, its query enumerable or not, and the first whose baseline answers 2xx is probed. With no endpoint of the right shape the rule skips, saying whether every such endpoint declares the family (or cannot be enumerated), none has a resolvable URL, or none answered a usable baseline — naming what each baseline answered.

**Pagination (§Pagination)** — `spec/pagination/links-enumerate-collection`, the kit's first multi-request, stateful rule. JSON:API 1.1: "The following keys **MUST** be used for pagination links: `first`: the first page of data, `last`: the last page of data, `prev`: the previous page of data, `next`: the next page of data", and "Keys **MUST** either be omitted or have a `null` value to indicate that a particular link is unavailable." The kit is never told the set a server pages over; it derives it, for every list or related endpoint that declares `page[limit]` or `page[size]` and whose URL resolves:

1. **The reference.** `GET` the endpoint with no page parameters. An answer without `next` is the whole collection; one with `next` is the server paging by default, and the reference is the walk of its own pages.
2. **The walk.** Again at a page size that forces a different partition: a third of the collection when it came back whole (about three pages), one fewer than the server's own page size when it pages by default. It sets `page[limit]`, else `page[size]`, on the first request only, and reaches every later page through `next` — so offset, page-number and cursor pagination are checked alike, off the links rather than the strategy.
3. **The verdict.** Each walk: the first page carries no `prev`; no resource is on two pages; `next` never leads back to a page already visited, to a page that lists no resources (the last page carrying `next`), to anything that is not a page of the collection, and is always a link; `first` and `last` on the first page answer the same resources as the first page and the last page the walk reached. Then the walk against the reference: every resource reached, and none the reference does not list.

**Why a `next` to an empty page is a MUST failure.** The base specification defines `next` as "the next page of data" and requires an unavailable link to be omitted or `null`. A page that lists no resources is not a next page of data: the page before it was the last, so its `next` was a link to a page that does not exist, where the spec required none. The [cursor-pagination profile](https://jsonapi.org/profiles/ethanresnick/cursor-pagination/) does allow such a link, but not on a page the walk reads `next` from. Its §Links holds a server to the same answer for any request without `page[before]`: "If a request does not contain the `page[before]` parameter, the server **MUST** determine whether a next page exists, and return `null` as the `next` link if not." The rest — a request that carries `page[before]` — falls to the sentences after it: "In all other cases, a server **SHOULD** set these links to `null` when it can inexpensively determine that the current response is for the first or last page respectively", and "if the server can't easily determine whether there are … subsequent results (when computing the `next` link), it **MAY** use a URI in these links that returns an empty array as its paginated data." The kit never adds `page[before]`: its first request sets only a page size, and every later request is a `next` link exactly as the server wrote it, which the profile's own examples spell with `page[after]` alone. So every page the walk reads `next` from falls under the profile's MUST, and a `next` there to an empty page fails under the profile as it does under the base specification. A server whose own `next` link carried `page[before]` would earn the MAY on the page it leads to; the kit does not recognise that case, and reads `next` as the base specification defines it. A page whose `data` holds items but none with a string `type` and `id` (or `lid`) is not taken for an empty page. The kit cannot say what such a page lists, so the walk is reported not decided. The page is not counted as empty. A walk that would start on such a page — the reference or the second walk — is not begun, and the collection is reported not decided, since nothing such a walk found could be held against resources the kit never saw.

The walk is bounded in requests, so a hostile or broken pager cannot keep the kit walking forever or make the rule die: 20 pages per walk, 200 requests per run of the rule (the `first` / `last` checks and the order recheck below included), and a `next` that leads back to a visited page, or to a page adding no resource not already seen, ends it with a finding. It is bounded in time by `requestTimeout` (§1.5, thirty seconds unless the run says otherwise), which bounds each of those requests; a run that turns it off is held by a server that holds one response open, as for every other rule. A request the timeout cuts short is a lost response, so it leaves the collection not decided. `skip: ["spec/pagination/links-enumerate-collection"]` leaves the walk out altogether (§1.5). A collection the budget runs out on, at any of those requests, is reported not decided, naming the budget. It is never a partial pass. A server error, a `429`, a `408` (RFC 9110 §15.5.9: the server "did not receive a complete request message within the time that it was prepared to wait") or a lost response mid-walk, or from a `first` / `last` link, says nothing of the links, so it leaves the collection not decided, as it does for the reference request. A `next` that leads to any other 4xx, or to a 2xx that is not a page, is a finding. A link resolves against the page that carries it, and one that leads to another origin is not followed (`Skipped`, naming the origin). Server values in findings render as `resourceLabel` and `Formatter.format` render them, so a link that is `{"toString":1}` is a finding, not a dead rule.

**An unstable order is not a violation of the links.** §Sorting: "The server **MAY** apply default sorting rules to top-level `data` if request parameter `sort` is not specified" — without `sort`, JSON:API requires no stable order, so offset pagination over rows that shift between requests may repeat or skip a resource without any link being wrong. So when the walk finds a problem that depends on order (a resource repeated or never reached, a `first` / `last` page that disagrees), the kit asks for each walk's first page again; if one comes back in a different order, those findings are withheld and the collection is reported not decided, quoting §Sorting. A recheck the budget leaves no request for, or that gets no page back, confirms nothing, so it withholds them too. This holds on every path out of the rule, including a walk cut short. The order-independent findings — `prev` on the first page, a `next` that cycles, dangles or is not a link — stand either way. Over an order that two identical requests reproduce, a repeat or a gap means `next` was not "the next page of data", so the rule is a MUST, the spec's own level. A server whose collection changes during the walk (a live server under writes) can show the same symptoms; the finding names the pages so they can be compared.

The rule skips, saying which, when no list or related endpoint declares a page size, when a collection holds fewer than two resources (no page size forces a second page), when the server answers every resource on one page at the size the kit asked for (it does not page at that size), or when the reference request is not answered 2xx with a resource collection the kit can identify. It costs about six to ten requests per collection.

**Links (§Resource Links, §Related Resource Links, §Fetching Resources, §Fetching Relationships)** — seven rules that follow the server's own links, because nothing in the type system ties a link _string_ to the route that serves it: a refactor that moves a path leaves every emitted link pointing at a 404 while every test that asserts on the document still passes.

| Rule | Level | Follows | Expects |
| --- | --- | --- | --- |
| `spec/links/resource-self-dereferences` | MUST | every resource object's `links.self` | the same `(type, id)` as primary data. §Resource Links: the links object "**MAY** contain a `self` link that identifies the resource represented by the resource object", and "A server **MUST** respond to a `GET` request to the specified URL with a response that includes the resource as the primary data." |
| `spec/links/related-dereferences` | MUST | every relationship's `links.related` | a 2xx with resource data as primary data: a resource object (an object with a string `type`), an array of them or `null`. §Fetching Resources: "A server **MUST** support fetching resource data for every URL provided as: … a `related` link as part of a relationship-level links object"; §Related Resource Links: "If present, a related resource link **MUST** reference a valid URL, even if the relationship isn't currently associated with any target resources." |
| `spec/links/related-matches-linkage` | SHOULD | the `links.related` of every relationship that also carries linkage (`data`) | the resources the linkage names. §Related Resource Links: "A "related resource link" provides access to resource objects linked in a relationship. | `spec/links/relationship-self-dereferences` | MUST | every relationship's own `links.self` (the relationship link) | a 2xx with resource linkage as primary data: `null`, a resource identifier object or an array of them — identifier objects only — of the cardinality the relationship's linkage shows or, for a links-only relationship, the relationship endpoint its link resolves to declares. §Fetching Relationships: "A server **MUST** support fetching relationship data for every relationship URL provided as a `self` link as part of a relationship's `links` object", and "The primary data in the response document **MUST** match the appropriate value for resource linkage". |
| `spec/links/relationship-self-matches-linkage` | SHOULD | the `links.self` of every relationship that also carries linkage (`data`) | the identifiers the linkage names. §Relationships, of the relationship link: "When fetched successfully, this link returns the linkage for the related resources as its primary data." |
| `spec/links/top-level-self-dereferences` | MUST | every document's top-level `links.self` | a 2xx with resource data as primary data. §Fetching Resources: "A server **MUST** support fetching resource data for every URL provided as: a `self` link as part of the top-level links object …". |
| `spec/links/top-level-self-matches-document` | SHOULD | every document's top-level `links.self` | a document of the same kind (below). §Document Top Level: `self` is "the link that generated the current response document". |

The levels follow the keywords. The `self` rule is the spec's own MUST sentence. For `related`, the MUST is §Fetching Resources' "support fetching resource data", so `related-dereferences` holds a link only to answering resource data. Which resources it must answer is §Related Resource Links' definition, which is declarative ("are returned") and carries no keyword, so `related-matches-linkage` grades it SHOULD (owner decision on 2026-10-09). The two follow the same links and are never both failed by one: a `related` link that does not parse, answers a non-2xx or answers something other than resource data is `related-dereferences`' finding, and `related-matches-linkage` leaves it not decided, naming that rule. The two `self` links split the same way (owner decision on 2026-10-15). For a relationship's `self`, the MUST is §Fetching Relationships' "support fetching relationship data" and "**MUST** match the appropriate value for resource linkage", which `relationship-self-dereferences` reads as the answer's _shape_: resource linkage, identifier objects only, as many as the relationship holds. Which identifiers it names is §Relationships' definition of the relationship link ("returns the linkage for the related resources"), which carries no keyword, so `relationship-self-matches-linkage` grades it SHOULD. For the top-level `self`, the MUST is §Fetching Resources' "support fetching resource data", so `top-level-self-dereferences` holds the link only to answering resource data; that the answer is the same document comes from the definition of top-level `self` (the link that _generated_ the document), which carries no keyword either, so `top-level-self-matches-document` grades it SHOULD and holds it only as far as that definition settles it (below). As for `related`, each SHOULD leaves a link its MUST fails — one that does not parse, answers a non-2xx, or answers something its MUST rejects — not decided, naming that rule, so one broken link is never failed twice.

The links are collected from one `GET` of every read endpoint whose URL resolves (list, single-resource and related endpoints; a relationship endpoint answers identifiers, which carry none — though its document carries a top-level `self`, so `top-level-self-dereferences` searches relationship endpoints too), from primary data and any `included`. A link may be a string or a link object's `href` (§Links: "a link **MUST** be represented as either: a string whose value is a URI-reference …, a link object or `null` if the link does not exist"); one that is neither is a finding, rendered as `Formatter.format` renders it. Each link is resolved against the document that carries it and followed once: a link to a URL the rule already fetched (an article's `self` on the article's own endpoint, say) costs no request. What the answer is held to:

- **`self`**: a 2xx whose `data` is a resource object of the same `type` and `id`.
- **`related`** (`related-dereferences`): a 2xx whose primary data is a resource object, an array of them or `null`, whatever the linkage says. A resource object is an object with a string `type`, so `{"data":"x"}`, `{"data":["x"]}` and `{"data":[{"id":"1"}]}` are findings. A links-only relationship (as every `Relationship.paginated` is) has nothing more to be held to.
- **`related`, to-one linkage** (`related-matches-linkage`): that resource as primary data; for `null` linkage, `null`.
- **`related`, to-many linkage** (`related-matches-linkage`): the same set of identities, with no order. A side that is a page relaxes it to a subset: when the answer carries `next` (the related collection pages), every resource it lists must be in the linkage; when the relationship carries `next` (the linkage pages — §Relationships: "Any pagination links in a relationship object **MUST** paginate the relationship data, not the related resources"), every resource the linkage names must be in the answer. When both are pages, nothing can be compared, and the link is not decided.
- **A relationship's `self`** (`relationship-self-dereferences`): a 2xx whose primary data is resource linkage — `null`, a resource identifier object, or an array of them. A resource identifier object here is an object with a string `type` and a string `id`, and no member but those, `lid` and `meta` (§Resource Identifier Objects), so a full resource object — one carrying `attributes`, `relationships` or `links` — is a finding, naming the members that do not belong. An identifier naming its resource by `lid` alone fails too: a `lid` stands for a resource not yet assigned an `id`, and what a relationship's `self` answers is stored ([owner decision](https://github.com/thomasfosterau/effect-jsonapi/issues/309#issuecomment-6203328372)). An @-member, which §Member Names has a processor ignore, and an extension member (`ns:member`: an alphanumeric namespace, one colon and a name) are not the base specification's to judge, so neither is a member that does not belong; whether the answer applied that extension is not checked, and a name with a colon anywhere else (`:x`, `a:`, `a:b:c`) is a member that does not belong. The cardinality must be the relationship's: when the relationship object's linkage is `null` or one identifier (to-one), the answer must be `null` or one identifier; when it is an array (to-many), an array. A links-only relationship (every `Relationship.paginated`, through `Handlers.paginatedRelationship`) shows no cardinality of its own, so the kit reads the one the api declares: discovery records, for each relationship endpoint (`Endpoint.getRelationship`), whether its success schema's `data` encodes as an identifier or `null` (to-one) or as an array (to-many), and a links-only relationship's `self` link whose path, under the run's base URL, fills a declared relationship endpoint's path is held to that endpoint's cardinality; the finding names the endpoint as the source. A link that resolves to no declared relationship endpoint (another origin, an undeclared path), or to one whose success schema shows no cardinality (a hand-built or `Schema.Unknown` success), is held only to answering linkage of either kind. A non-2xx is a finding expecting "resource linkage" whether or not the relationship carries linkage, since this rule holds the shape and not the identifiers.
- **A relationship's `self`, against its linkage** (`relationship-self-matches-linkage`): when the relationship object carries linkage (`data`), the answer is compared with it exactly as `related-matches-linkage` compares a `related` answer: the same identifier for to-one, `null` for `null`, and for to-many the same set of identities in any order, relaxed to a subset when either side carries `next`, and not decided when both do. An identifier named only by `lid` fails `relationship-self-dereferences`, so this rule leaves the link to it, not decided.
- **The top-level `self`** (`top-level-self-dereferences`): a 2xx whose primary data is resource data — a resource object, an array of them or `null`, as for `related`. A relationship endpoint's identifiers are objects with a string `type` too, so its document's `self` holds.
- **The top-level `self`, against its document** (`top-level-self-matches-document`): a document of the same kind as the one carrying the link. A single resource must answer that resource (the same `type` and `id`); `null` primary data must answer `null`; a collection must answer a collection (an array as primary data). A collection is compared resource for resource — the same set of identities, in any order — **only when neither document carries a `next` or `prev` link**: a page, on either side, may legitimately list other resources than the document it is compared with (the window moved, the server added a default page size to the `self` it wrote, or the order is unstable), so a page is held only to answering a collection. Order is never compared. Most servers write the URL that was requested as the `self`, which the rule has already fetched, so such a link costs no request and holds; the rule earns its keep when a server writes a `self` that differs from the request — a canonicalised query, a path the router no longer serves.

**What the kit cannot identify, it does not decide on, on either side.** An answer listing an item without a string `type` and `id` leaves the link not decided. So does a claim the kit cannot read: a resource object with no string `type` and `id` cannot have its `self` held to it, and linkage naming such an item cannot have its `related` held to it. Such a link is noted as not decided, without a request, rather than dropped (the `self` case) or compared with the unidentified item left out (the linkage case, which would report a resource the linkage does name as one it does not).

The crawl is the pagination walk's (`src/internal/conformance/crawl.ts`, shared): `GET` only, and a link that leads to another origin (scheme, host or port) is never requested and is reported not followed; one whose scheme gives it no origin (`javascript:`, `data:`) is named by its scheme. A redirect is followed only within the base URL's origin (§1.2), each hop counting against the budget, and the answer it leads to is what the link is held to; one the kit does not follow — off the origin, past five hops — leaves the link not decided and the rule `Skipped`, naming its `Location` (§1.2), so a link cannot reach another origin that way either. A server error, a `429`, a `408` or a lost response leaves that link not decided, never failed. So does a `401` or `403`: access control is outside JSON:API, so a link the kit may not follow is not a broken one. Any other non-2xx — a `404`, or a `3xx` with no `Location` to follow — is a finding: the run has just received the link from the server, so a 404 for it is the server contradicting itself (a live server under writes can legitimately delete a resource between the two requests; the finding names both, so they can be compared). Each rule may make 200 requests per run, the collecting `GET`s included. A crawl the budget cannot finish — a read endpoint it had no request left to search, or a link it had none left to follow — is `Skipped`, naming the budget and how far it got, never a partial pass, unless a link it did follow already broke the rule, which stands. Like the pagination walk, the crawl is bounded in requests, and in time by `requestTimeout` (§1.5) unless the run turns it off; a request the timeout cuts short is a lost response, which leaves its link not decided. `skip: ["spec/links/"]` leaves the crawl out altogether (§1.5). A rule that decided some links and not others passes with a note naming each it could not decide; with none decided it skips, saying why. With no link to follow it skips, naming the endpoints it searched and how each that did not answer 2xx answered. A failed rule lists its first ten findings and one more counting the rest, and every server value a finding names — a resource's `type:id` included — is quoted cut to 200 UTF-16 code units, so a server with a broken link on every resource, or an id a megabyte long, does not make a report of the same size.

**Status codes** — 404 for an absent resource. With the write fixture: a creation without a client-generated id answers 201 with the created resource as primary data (`create-response-document`); the 201 carries `Location` (`create-location`, a SHOULD — the spec's level, corrected from the MUST the never-run v1 rule claimed) and, when the resource also carries `links.self`, the two match (`create-location-matches-self`); an update answers 202, 200 with a document whose primary data — when it has any — is the updated resource (JSON:API 1.1 lets a 200 carry no primary data when the server changed nothing beyond the request; the document must then still be one, so the kit wants a top-level `meta` and no `errors`), or 204 with no response document (`update-response`); and a delete answers 204 empty, 200 with only `meta`, or 202 (`delete-response`; a `400` to a delete sent without a key, from an endpoint declaring `Idempotency-Key`, whose error names `source.header: idempotency-key` decides nothing, §1.4 — any other refusal fails, a `409` or `422` naming the header included). A create of the fixture's payload under a `type` no endpoint serves (`conformance-unserved-type`) answers 409 (`create-conflict-type`); any other status fails, a 400 included — what `Endpoint.create` answered until which made `Middleware.SchemaErrorsLive` answer a string `data.type` the endpoint does not serve with the 409. A server that wrongly creates something is vetted against the fixture's own type and disposed of like any other create. Writes are read back through the type's single-resource `GET` (`/<type>/:id`): the resource a 201 carried must read back with the same `attributes` and relationship linkage (`create-read-back`), and after an update, what a 200 carried — or, for a 204 or a 200 without primary data, which mean the server changed nothing beyond the request, the request's own `attributes` and linkage (`update-read-back`). Only members the write stated are compared, so an attribute only the read shows (a default fieldset) is no finding; a to-many linkage is compared in any order; a `404` or `410` is a write that was not stored. A read-back the server cannot answer (a 5xx, a refusal, no answer), a 202, or a type with no `GET` endpoint decides nothing. With a fixture's `clientId`: where it declares client-generated ids supported, a create carrying `clientId.id()` as `data.id` answers 201 with that resource — under that id — as primary data, or 204 with no document (`create-client-id`; a 202 decides nothing, and a 201 under another id is the finding of a server that dropped the id), and a second create of a fresh payload under the same id, while the first holds it, answers 409 (`create-conflict-id`; it runs only once the first create made a resource under the id, and anything a wrong 2xx makes is vetted and disposed of — a second resource named under the first's live id is refused and left untouched); where it declares them unsupported, a create under one answers 403 (`create-client-id-unsupported`; any other status fails, a 2xx noting the id the server created under), and one of its error objects must carry a `source.pointer` naming the resource object's id, `/data/id` (owner decision on following the atomic rule's): a 403 with no pointer fails, as does one naming only some other member — what `Endpoint.create` answers since [#450](https://github.com/thomasfosterau/effect-jsonapi/issues/450) for a payload that declares no `data.id`, at `/data/id` since [#463](https://github.com/thomasfosterau/effect-jsonapi/issues/463).

**Relationship mutation (§Updating a Resource's Relationships)** — with the write fixture, for each `PATCH` / `POST` / `DELETE` on `/<type>/:id/relationships/<name>` whose type has a `create`: a created resource's linkage is replaced with the `ids` sample of a type the payload names — the identifier for a to-one relationship, `[identifier]` for a to-many one — and must read back as exactly that (`spec/relationships/update-replaces`); a to-one relationship whose payload admits `data: null` (discovery reads it off the payload schema, so a required one, `Relationship.one`, is not decided) is linked to the sample when it reads back empty, then cleared with `{ "data": null }`, and must read back as `null` (`update-to-one-null`); the sample is added to a to-many linkage read beforehand, which must read back as it was plus the sample (`add-appends`); and it is removed from one that holds it — linked first through the relationship's `POST`, or failing that its `PATCH`, when it does not — which must read back as it was less the sample (`remove-deletes`). Each read-back is through the relationship's own `GET /<type>/:id/relationships/<name>`, compared in any order; an endpoint without one is not decided. A read-back rule judges only the read-back: a write the server does not accept (a `403` included, which the specification allows for a replacement or removal it does not permit) decides nothing, nor does a `202`, a `POST` / `DELETE` whose payload declares a to-one relationship, or a read that answers no linkage; a `404` or `410` on the final read is a finding. What each of those writes answers is judged too (`write-response`): a `202`, a `204` with an empty body, or a `200` whose document carries the linkage as it now stands — compared, in any order, with what the relationship's `GET` then reads back, or, with no such `GET` (so a `PATCH` is judged where the read-back rules cannot be), with what the write leaves — or carries no primary data, a top-level `meta` object and no `errors`. Any other 2xx, a `204` with a body, a `200` with no document, an `errors` document or primary data that is not linkage is a finding; a write the server does not accept decides nothing. And a `PATCH` or `POST` naming `absentId` under the first type the payload names must answer 404 (`absent-related-404`): a `403` (the write not permitted at all), a `5xx` or no answer decides nothing, and any other status — a 2xx linking it, a `400` or `422` refusing it — is a finding. A `DELETE` naming `absentId` instead must succeed (`remove-absent-succeeds`): a resource that does not exist is already missing from the relationship, and §Updating To-Many Relationships requires a successful response when every specified resource is "able to be removed from, or [is] already missing from, the relationship". Its answer is judged as `write-response` judges any write — a `200` carrying linkage against what the relationship's `GET` then reads back, and with no such `GET` not decided. A `403` (the removal not permitted at all) or no answer decides nothing; a `404`, or any other error, is a finding.

**Atomic operations** — a malformed `atomic:operations` document is rejected (any 4xx to a document sent without a key whose error names `source.header: idempotency-key` — the missing-key `400`, a `409` or a `422` — decides nothing, since a refusal over the key says nothing of whether the document was examined, §1.4); with the write fixture, an `add` of the fixture's payload is answered under the extension's media type (`response-ext-parameter` — a §Content Negotiation universal-responsibility MUST: whoever applies an extension names it in `ext`). Processing is judged by what the server stored, read back afterwards, never by its answer alone — save `remove-absent-succeeds`, whose request changes nothing to read back, and each probe builds its `add` operations from the write fixture, records what they created and disposes of it, latest first, however the rule ends:

- `lid-resolution` (MUST) `add`s a resource under a `lid` and names it by that `lid` in a second operation of the same request. When one fixture's payload links to another fixture's type, the second operation is that payload's `add`, linking by `lid` instead of `id`; both resources are read back, and the linking one's relationship must name the other by the id the server gave it. When the fixture has an `update`, the second operation is an `update` naming the new resource by `lid`; it is read back by its server-assigned id and must show the patch. The blog's fixture links only to a person, which no fixture creates, so the blog runs the update probe.
- `all-or-nothing` (MUST) lists the type's collection (following `next`, within 20 requests), sends an `add` followed by a `remove` naming a `lid` no operation assigned, and lists the collection again. The request must be refused with an error document, and a resource that appeared in between carrying the fixture's `attributes` is one the server applied anyway: a finding, and the kit records it and hands it to `cleanup`. A resource that appeared with other attributes (someone else's) is neither counted nor touched. A server that answers the request with a 2xx failed no operation, so the rule is not decided by it (what it created is disposed of).
- `results-order` (MUST) sends an `add` and then a `remove` of the same resource by `lid` — one operation with data, one without — and requires `atomic:results` to hold two result objects in that order: the created resource first, nothing second. A short list or a reversed one fails; a `204`, or results that cannot be told apart, decide nothing. The resource is read back afterwards, and recorded as `deleted` when the request's own `remove` removed it.
- `remove-absent-succeeds` (MUST) `add`s a resource, then sends a `remove` on one of its to-many relationships naming `absentId` under a type that relationship links to. The atomic counterpart of the relationship rule of the same name: the resource is already missing from the relationship, so the request must answer `200` or `204`. Which relationships the operations endpoint accepts is not discoverable, so the relationship is the first to-many one a `/relationships/…` write endpoint of the type shows; a type with none is not decided. A `403`, a refusal over `Idempotency-Key`, or no answer decides nothing; a `404`, or any other status, is a finding.

With a fixture's `clientId` the extension's `add` is held to the client-generated id rules a `POST` is, one `add` per request, so a refusal — which applies nothing — is taken to have created nothing, and whatever a 2xx made is vetted and disposed of as any create's. Where the fixture declares client ids supported, an `add` carrying `clientId.id()` as `data.id` answers 200 with its result carrying that resource under that id, a result with no `data`, or 204 (`add-client-id`; a 202 decides nothing, and a result under another id is the finding of a server that dropped the id), and a second `add` of a fresh payload under the same id, sent once the first holds it, answers 409 (`add-conflict-id`). Where it declares them unsupported, an `add` under one answers 403 (`add-client-id-unsupported`), and one of its error objects must carry a `source.pointer` naming the operation's id, `/atomic:operations/0/data/id`: a 403 with no pointer fails, as does one naming only the operation (`/atomic:operations/0`) or `/data/id`, as a create endpoint's refusal names it, which points at nothing in an atomic document. The create endpoint's `create-client-id-unsupported` is held to its own id's pointer, `/data/id`, in the same way. A refusal naming `/atomic:operations/0/data/type` is the operations endpoint not taking the type, and decides nothing. `Endpoint.operations` answers the 403 at `/atomic:operations/N/data/id` since [#464](https://github.com/thomasfosterau/effect-jsonapi/issues/464).

**The failure mode is a reference to an absent `lid`, not a fixture-supplied invalid operation**. It is available against every server — `remove` and `lid` are part of every operation union `Endpoint.operations` builds, and of the extension itself — and needs nothing more from the caller. It is valid against the operation schema, so it reaches processing rather than stopping at the decoder: a schema-invalid operation may be refused before any operation is applied, which tests the codec, not the extension. And a `lid` names a resource only once an earlier operation of the same request has assigned it, so a server that resolves it some other way has broken `lid` resolution too. It is insufficient only against a server that answers such a request with a 2xx; the rule then reports why it decided nothing rather than passing. A fixture-supplied failing operation can be added if a server turns up that needs one.

**The profile tier** — the filter grammar's advertisement (§5), its rejections with `source.parameter` (§2, §4, §7: an operator outside the closed core, an undeclared field, a key deeper than the grammar admits, a repeated `filter[…]` key), and spelling equivalence (§2.2, §3: bare shorthand, explicit `[eq]`, group form and a key-permuted group form must all answer the same document, because the canonical string is a function of the AST alone), spelt on the first string attribute of the first resource the endpoint answers, its literal escaped per §2.3. The grammar's evaluation semantics (§6) are `profile/filter/evaluation`: on each collection endpoint speaking the grammar whose answers advertise the profile, the kit walks the collection unfiltered (its `next` links followed, so a paginated collection is compared whole), builds filter trees over the fields it carries, evaluates each with the kit's own §6.3 fold, and compares the match set with the filtered collection's on `(type, id)`, naming every resource wrongly included or wrongly excluded and the value the tree read on it. The trees come in families, each judged on the first field (of up to three) the server decides anything on. `And([])` and `Or([])` (F-AND-2) need no field. On an attribute that is NULL (or absent) on some resources and a JSON scalar of one type on others, the trees that tell three-valued evaluation from two-valued: `ne`, `gte`, `lt`, `lte` and `gt` over NULL (F-CMP-1, F-CMP-2, F-ORD-1), `nin` (F-IN-2, F-IN-3), `isnull=false` and `isnull=true` (F-ISNULL-1, F-ISNULL-2) and `Or(eq, Not(eq))` (F-CONS-1). On an attribute the sample never shows NULL, with two or more values, `lt`, `lte`, `gt` and `gte` at a pivot — the median of its values in F-ORD-1's order — so each splits the sample and a server ordering numbers as text, or under a locale, is caught (F-CMP-2, F-ORD-1), and `isnull=true`, which F-ISNULL-4 makes match nothing. On a to-one relationship every resource shows linkage for, valued by the related id (F-EVAL-4, F-ORD-5) — one whose linkage is empty on some resources first — `eq`, `ne` and `nin`, and `isnull` both ways where the linkage is empty on some (F-CMP-1, F-IN-2, F-ISNULL-1); never an ordering operator, which F-ORD-5 rules out, and never a relationship that shows no linkage (links only), whose value the kit cannot know. And, where the endpoint declares `fields[TYPE]` for the one type it serves, `eq` on such a field beside a sparse fieldset naming another field instead (F-EVAL-6): the match set must be the same as without the fieldset. The §6.5 corollaries ride on the same fold, over the first field that decides — an attribute NULL on some resources, then a to-one relationship empty on some, then the rest — with `a` its `eq` on a value the sample carries and `b` its `isnull=true`: `Not(And(a, b))`, `Or(Not(a), Not(b))`, `Not(Or(a, b))` and `And(Not(a), Not(b))` (F-CONS-2), `Not(In(f, values))` (F-CONS-3), `Not(Not(a))` (F-CONS-4), and `Or(Not(b), Not(a))` again in a second spelling of its canonical form, group ids renamed and every key reversed so each member precedes the group it names (F-CONS-7). Where the endpoint declares `include`, `eq` on a field beside `include` of the first relationship the sample shows linkage through, which must leave nothing the matched primary data links to out of `included` (F-CONS-6). And every filter sent alone is held to F-CONS-5: each resource it answers must be the resource the collection serves unfiltered (`attributes`, `relationships`, `links` and `meta` alike), and its first page must be a 200 collection document — a 200 that is not one, or a 404 where the fold matches nothing (F-ERR-2), is a finding, not a refusal. Each literal is one the sample carries, so the comparison domain is the JSON type the server answered — the kit infers it rather than reading it off a resource definition. A filter the server refuses (a 400: the field may not be filterable, or not with that operator) decides nothing here, since the rejection rules judge refusals; a family with no field to probe is named in the outcome's note with why — no attribute NULL on some resources, none never NULL with two values, no to-one linkage shown, no `fields[TYPE]` or `include` declared — rather than passing silently. The Idempotency-Key profile's advertisement (`docs/idempotency.md` §1, a SHOULD): with the write fixture, one create per create endpoint that declares `Idempotency-Key`, and one create plus one update (the `update` fixture) per update endpoint that declares it, the create judged too when its endpoint declares the header. A create endpoint is not probed on its own for a type an update endpoint covers, so a type with one update endpoint gets one create and one update; a type with several (a `PATCH` and a `PUT`) gets one of each through every one, as the spec tier's `update-response` does. A create and an update count as two requests either way. Each 2xx must name the profile URI in `jsonapi.profile` (what `Idempotency.jsonapi` produces) or in the media type's `profile` parameter; either passes, since §1 makes the media type a MAY. A media type naming it passes even with no body; a write the server does not accept, or a 2xx with no document whose media type does not name it, decides nothing. The kit sends a fresh `Idempotency-Key` only to an endpoint that requires one (`idempotency: "required"`), as every write rule does; where the key is optional it sends none. Plus two library conventions: advertising `jsonapi: { version: "1.1" }` and accepting the repeated-key spelling of every comma-separated family.

**Sort order** — `profile/sort/ordering` (`src/internal/conformance/sort.ts`), the profile's [§10](./filter-grammar.md#10-sort-order): `?sort=f` lists the primary data in ascending F-ORD-1 order of `f`'s JSON value, NULLs (an absent member or `null`) last, and `?sort=-f` in exactly the reverse, NULLs first (S-ORD-1 to S-ORD-3). It is read-only and needs no fixture, because the order is read off the answer itself. For every list or related endpoint that declares `sort` (S-SCOPE-1; relationship endpoints answer identifiers, with no value to read an order off, and are not probed) and whose URL resolves, the kit:

1. `GET`s the endpoint once, and picks the attributes whose values there could show an order at all: two distinct values at least, NULL counting as one, all of one JSON scalar type besides NULL (S-KEY-2). Those holding a NULL go first, so NULL placement is checked wherever the collection shows one.
2. Sends `?sort=f` and `?sort=-f` for each, and holds each answer's primary data to its order, adjacent pair by adjacent pair. A finding names the first pair out of order, the values and which rule a NULL broke, with the whole sequence as served. An answer that pages is its first page, a prefix of the order (S-PAGE-1), and is held to the order as it is.
3. Stops at the first attribute holding a NULL in its answers, or at the second decided, whichever comes first.

A `400` to `?sort=f` is the server refusing that attribute (§Sorting), not a statement about order, so the next attribute is tried. An answer that is not a 2xx resource collection, or that holds fewer than two distinct values or values of more than one JSON type, decides nothing for that attribute; a finding the ascending answer already made stands. The rule skips, naming why for each endpoint, when no list or related endpoint declares `sort`, when no attribute could be decided anywhere (a single resource, every attribute refused, every sorted request failing), and passes with a note when NULL placement was never observed (no decided attribute held a NULL) or an endpoint was not decided. It makes at most 60 requests per run — about three per endpoint — and notes the endpoints the budget left unprobed.

Three more rules check the rest of §10 the same way, each with its own baseline per endpoint, the same refusal and not-decided handling, and its own request budget:

| Rule | Level | Sends | Expects |
| --- | --- | --- | --- |
| `profile/sort/multi-field` | MUST | for an attribute `a` two resources of the baseline tie on, and an attribute `b` that tells some tied resources apart (an `a` that also shows two distinct values first), `?sort=a,-b` and `?sort=-a,b` | each answer in lexicographic order of its two terms, each in its own direction (S-MULTI-1); a finding names the first adjacent pair out of order, with both values. Whichever order a server that ignores the second term breaks `a`'s ties in, one of the two requests contradicts it. An answer that lists no two resources tying on `a` and differing on `b` decides nothing. At most 40 requests a run, three pairs tried per endpoint. |
| `profile/sort/id-tiebreak` | SHOULD | for an attribute two resources of the baseline tie on (NULL ties NULL, S-ORD-4), `?sort=f` and `?sort=-f` | every pair of identified resources that tie on `f` in the first answer listed in the same relative order in the second: the tiebreak is a fixed order on `id`, applied after the last term whatever its direction (S-TIE-1, S-TIE-2). A server that answers `-f` by reversing its answer to `f`, or whose tie order differs between the two requests, fails; the finding names the first pair swapped and counts the rest. It does not hold the tie order to code-point or numeric `id` order, which S-TIE-2 recommends but does not require. At most 40 requests a run, three attributes tried per endpoint. |
| `profile/sort/across-pages` | MUST | for every list or related endpoint that also declares `page[limit]` or `page[size]`, `?sort=f` with that size set to half the baseline's count, walking `next` (at most ten pages, never off the origin or back to a page already visited) | every resource on a page after every resource on the page before it, under `f`'s ascending order (S-PAGE-1): each page's last value in that order is held against the next page's first. Each page's own order is `profile/sort/ordering`'s to check. A walk that reaches only one page — a server that ignores the size — decides nothing; one cut short still decides on the pages it fetched, two at least. At most 60 requests a run. |

The grammar rules learn a field name the target is known to accept from a baseline response before probing rejections — otherwise "undeclared operator" would pass for the wrong reason, since an undeclared _field_ is also a 400.

### Vacuous passes are the failure mode

A conformance kit that answers "OK" without saying what it checked is worse than nothing, because it manufactures confidence it has not earned. Three mechanisms guard against it:

1. **Applicability gating.** A conditional rule that never met its condition reports `Skipped`, not `Passed`. `spec/document/full-linkage` over an api that returned no compound document says so; `spec/document/jsonapi-object` over documents with no `jsonapi` member says so; `spec/query/sparse-fieldsets-included` counts only projection probes that actually returned an `included` resource of the requested type.
2. **Three distinct kinds of "not checked".** A rule can be absent because this api has no endpoint of that shape, because the caller withheld a sample id, or because the kit does not implement it at all — and the report keeps them apart. A reader who cannot tell them apart does not know what the run proved.
3. **A declared coverage ledger.** `Conformance.gaps` lists the areas the kit does not check, each with its reason and its tracking issues, and `format` prints it in every report. A requirement named neither in `Conformance.rules` nor in `Conformance.gaps` is simply unwritten, and the ledger says so in as many words.

The summary line reports skips alongside passes for the same reason:

```
SUMMARY  7 rules failed (19 findings) · 19 passed · 10 not checked · 7 areas out of scope · 111 requests made
```

#### The four outcomes

Every rule in a run ends in exactly one `Conformance.Outcome`, and the four mean different things:

| Outcome | Means | Is it a verdict on the server? |
| --- | --- | --- |
| `Passed` | The rule ran, made its probes (`probes` counts them) and found nothing. | Yes: it held. |
| `Failed` | The rule ran and found the server breaking it; `findings` says how, with the request. | Yes: it is broken. |
| `Skipped` | The rule could not be decided against this target — no endpoint of that shape, a withheld `ids` sample or `writes` key, a condition never met (§4 above), a write payload the server rejected or a `writes` `create` / `update` that threw — and `reason` says which. | No: a statement about coverage. |
| `Errored` | The rule **died** before it reached a verdict: a transport that throws, or a bug in the kit. `message` renders the defect and `defect` is the value as thrown. | No: the run could not decide it. |

A rule that skips was _never going to_ be decided against this target; a rule that dies _should have been_ and was not. A throwing fixture is neither: a `create` or `update` that throws skips the rules it was for, naming the member, and a `cleanup` that fails or throws is recorded in `Report.writes` as `cleanup-failed`. Since a rule's defect is that rule's `Errored` outcome rather than the end of the run: every other rule still runs and is reported, and so is `Report.writes`, so the cleanup ledger survives one bad rule. (Before, the defect failed the whole `verify` / `verifyWith` and took the rest of the report with it.) Interruption is not turned into an outcome — it is a request to stop the whole run, not something one rule did, so it still stops it.

How each reading of a report treats it:

- **`format`** prints each tier's dead rules first, marked `DIED`, with the defect's message in place of findings. The tier and summary lines gain a `· N died` count — only when a rule did, so a clean run's summary reads as above.
- **`summarise`** counts them in `errored`, separately from `failed`, `passed` and `skipped`.
- **`assert`** dies on the first `Errored` outcome, before it looks at failures, with a defect that names the rule and carries the original defect as its `cause`. It does not fail with a `ContractViolation`, because a dead rule is not a finding about the server, and it cannot pass, because the rule was not decided — so a gate built on `assert` is exactly as strict as when a defect killed the run.
- **A gate that does not use `assert`** must check for dead rules itself. A test that filters `outcomes` for `Failed` — for instance to pin a known set of failures — lets an `Errored` rule through silently. Gate on `Conformance.summarise(report).errored === 0` as well, and print `Conformance.format(report)` when it is not.

### What v1 does **not** cover

Declared in `Conformance.gaps` and printed in every report.

| Area | Why not |
| --- | --- |
| **The filter profile's evaluation semantics, beyond what the sample shows** | `profile/filter/evaluation` decides every comparison operator, membership, `isnull`, excluded middle and the empty groups over the attributes and to-one relationships the unfiltered collection shows, a filter beside a sparse fieldset (§3), and the corollaries F-CONS-2 to F-CONS-7. It can only probe what the sample holds: F-ORD-2's exact string comparison (no case folding, collation or normalisation) and F-ORD-3's sub-millisecond precision are tested only as far as the values the server holds exercise them, and a relationship that shows no linkage has no value to read. Each corollary is probed one way: F-CONS-5 holds the answered resources and an empty result's status and document, not the top-level `meta` and `links`, which may rightly carry the query or a count; F-CONS-6 follows one relationship, one level deep; F-CONS-7 respells ids, key order and member order, not a literal (F-COERCE-4). The refusals F-ERR-4 and F-ERR-5 are not probed. See §6. |
| **The Idempotency-Key profile** | Its advertisement is checked on create and update endpoints (§3). Delete endpoints (usually a 204, with no document to name it in) and the atomic operations endpoint are not checked. What a retried write does — replay, the fingerprint mismatch, the in-flight case, the scope of a key — needs the kit to resend a request byte for byte. |
| **Concerns outside JSON:API** | Auth, caching, conditional requests, rate limiting, CORS. The spec takes no position, so neither does the kit. |

Mutating probes are **off by default** (`mutating: true` opts in, and the write rules also need a `writes` fixture), because a conformance run should be safe to point at a live server.
