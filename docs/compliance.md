# Spec compliance

| JSON:API v1.1 rule | How it's enforced |
| --- | --- |
| Media type `application/vnd.api+json` | baked into every document/payload/error schema |
| 415/406 on media type parameters other than `ext` / `profile` (or unsupported extensions) | middleware attached to every endpoint; providing it is required by the type system |
| Error bodies are error documents | only `ApiError.make` classes can be declared as endpoint errors |
| Top-level document holds exactly one of `data` / `errors` / `meta` | success schemas only ever contain `data`; error schemas only `errors` — mixing is unrepresentable |
| `null` primary `data` only for a single-resource URL that might correspond to a resource but currently doesn't | `DataDocument` is a pure envelope: `DataDocument(R)` is non-null; opt into `data: null` with `Schema.NullOr(R)` / `R.nullable()`. `Endpoint.related` keeps the nullable form for a to-one relationship |
| Resource objects have `type` and `id`; ids are not interchangeable across types | `Resource` always emits the type tag and a per-type branded id |
| Create requests may omit `id` and send `lid` | `createPayload` derivation |
| 403 Forbidden for a create under a client-generated id the server does not support | `createPayload`'s resource object declares no `id` and rejects one at `/data/id`, and `Middleware.SchemaErrorsLive` answers it with a 403 whose `source.pointer` is `/data/id`, before the handler runs; a type or member that fails beside it is answered first, with the 409 or 400 it earns. An atomic `add` operation's resource object does the same, answered with a 403 whose `source.pointer` is `/atomic:operations/N/data/id` and no operation performed. To support client ids, pass `Endpoint.create` (or `Endpoint.operations`) a `payload` whose `data` (or whose `add`'s `data`) declares an `id` |
| Update requests require `id`, attributes are partial | `updatePayload` derivation |
| 409 Conflict for a create or update whose resource object's `type` the endpoint does not serve | `Endpoint.create` / `Endpoint.update` declare the type they serve, and `Middleware.SchemaErrorsLive` answers a string `data.type` naming another with a 409 whose `source.pointer` is `/data/type`; a `type` missing or not a string stays a 400. An update's `data.id` that differs from `:id` is the handler's 409 (`ResourceHandlers.make` answers it) |
| Relationships hold at least one of `data` / `links` / `meta` | `one` / `optional` / `many` schemas require resource linkage (`data`); `paginated` schemas require `links.related` |
| Relationship endpoints: GET/PATCH on to-one, GET/POST/PATCH/DELETE on to-many | `Endpoint.getRelationship` / `updateRelationship` / `addRelationship` / `removeRelationship`; add/remove only constructible for to-many relationships |
| Related resources requested from a relationship endpoint (`?include=` rooted at the relationship) | `Endpoint.getRelationship`'s `include` option legalises the parent's include paths rooted at the relationship and adds an `included` member to its linkage document; `Handlers.linkage`'s `included` checks full linkage from the identifiers. Its `fields` option declares `fields[TYPE]` for the types those paths reach, which narrows the `included` members only, the primary data being identifiers |
| Related resource endpoints (`related` links) | `Endpoint.related` — single-resource document with nullable `data` for to-one (empty-linkage case), paginated collection for to-many |
| Compound documents: no duplicate resources, full linkage | `Handlers.resolveIncluded` walks the requested paths into one `(type, id)`-keyed bucket, so its output is fully linked by construction; `Handlers.data` / `Handlers.collection` deduplicate against the primary data (`Handlers.linkage`, whose primary data is identifiers, only among the members) and check full linkage on the resources they emit, after `onResource` (runtime check — it catches an `included` member a transform has left unreachable, [so keep it on](handlers.md#resolving-included--one-batch-per-level)). The check walks reachability from the primary data — from the primary identifiers themselves when `Handlers.buildIncluded` is handed a relationship document's linkage — as [the conformance kit](conformance.md)'s `spec/document/full-linkage` does, so a document the builders accept passes that rule on the document value they build: a cycle of members the primary data does not reach, or a member referenced only by itself, throws. Encoding drops relationship keys the resource does not declare, so `Middleware.SchemaErrorsLive` re-runs the same walk on every 2xx document the endpoint encoded and answers a member reached only through an undeclared relationship with the opaque JSON:API 500, reported at `Error` severity; `Middleware.schemaErrorsLayer({ checkLinkage: false })` / `layerWith` turn that wire check off |
| Compound documents never inline unbounded relationships | `paginated` relationships are excluded from `?include=` paths and `included` unions by construction — except on their own relationship endpoint, whose primary data is one page of the linkage and whose `included` is held to that page by full linkage |
| `errors` array is never empty | non-empty check on the error document schema |
| 200 / 201 / 204 status codes per operation | set by the endpoint constructors |
| A 201 create carries `Location`, matching the created resource's `links.self` | `Endpoint.create` attaches `Middleware.CreatedLocation`, which copies the resource's (or the document's) `self` link into the header |
| Pagination / sorting / sparse fieldsets / inclusion / filtering query families | typed query schemas derived from the resource definition |
| 400 for a query parameter the server doesn't process: a reserved all-a-z name, a spec family the endpoint doesn't declare, a name that isn't a legal member name, an extension's parameter | the `SchemaErrors` middleware attached to every endpoint checks every name before decoding; `allowedQueryParameters` (default `["_"]`, jQuery's cache-buster) is the only escape hatch ([Reserved query parameters](handlers.md#reserved-query-parameters)) |
| Atomic operations extension: `atomic:operations` / `atomic:results` documents, lid refs, relationship operations | `Endpoint.operations` + `Atomic` schemas derived from resource definitions |
| Profiles are negotiated, advertised in `jsonapi.profile`, and unknown ones ignored | the filter grammar and idempotency profiles publish URIs; negotiation ignores profiles it doesn't know |

## Declaration emit

A project that compiles with `declaration: true` can export what it builds — an endpoint, a group, an `HttpApi`, a client — with no annotation, wherever the resources it is built over are defined:

```ts
// endpoints.ts
import { Endpoint } from "@thomasfosterau/effect-jsonapi";
import { Person } from "./resources.js";

export const getPerson = Endpoint.get(Person);
```

Declaration emit writes the value's inferred type into the `.d.ts`, so it must be able to name every type that type mentions, such as `Resource.Resource` and `Resource.Id` here. The TypeScript checker names a type only through a namespace the file imports itself or through a module that exports the type directly, never through a namespace alias like the root's `Resource`, and the module subpaths are those modules: it writes `import("@thomasfosterau/effect-jsonapi/Resource").Resource<"people", …>`. Before the subpaths, a resource imported from another file failed here with TS2883.

The type-only aliases at the package root (`QuerySchema`, `ContentNegotiation`, `ApiErrorWire`, `BadRequest`, …) served the same purpose for the single-file case. Declaration emit no longer needs them, and they are **deprecated** in favour of the subpaths: write `Query.QuerySchema`, or import it from `@thomasfosterau/effect-jsonapi/Query`. They remain exported for now. The checker still prefers a direct root export when it names a type, so your own emitted `.d.ts` may reference them (`import("@thomasfosterau/effect-jsonapi").ContentNegotiation`), which is why removing them later will be a breaking change for downstream published declarations.

## Limitations

- **Conformance coverage is partial, and says so**: the kit covers content negotiation, document structure, error objects, query-parameter handling, pagination links (following `next` must enumerate the collection), the links a document carries — a resource's `self`, a relationship's `self` and `related`, and the top-level `self` (each followed must answer what it names: the resource, the relationship's linkage, the related resources, the document) — the write rules (success responses, the 409 for a mismatched `type`, client-generated ids, and relationship mutation read back, what it answers, the 404 for linking a resource that does not exist and the success of removing one), the filter grammar profile with its evaluation semantics over NULL, and its sort order (`?sort=f` and `?sort=-f` must order by `f`'s JSON value, NULLs last ascending; several terms order lexicographically; the order holds across pages; and, a SHOULD, ties are broken by `id`). The rest of filter evaluation and what a retried idempotent write does are declared gaps rather than silent omissions — see `Conformance.gaps` and [`docs/conformance.md`](conformance.md).
- **Sparse fieldsets are opt-in, not automatic**: `?fields[TYPE]=` is decoded, validated and handed to your handler, and the builders project it when you ask them to — `Handlers.data(article, { included, onResource: Handlers.project(query.fields) })` ([the per-resource transform pass](handlers.md#the-per-resource-transform-pass-onresource)). Nothing is projected behind your back; the builders don't post-process responses against request state on their own. The default document of an endpoint declaring `fields` admits the projected answer, so its clients read those attributes as optional ([sparse fieldsets and the default document](handlers.md#sparse-fieldsets-and-the-default-document)). A fieldset names relationships as well as attributes (`?fields[articles]=title,author`), and `Handlers.project` drops the relationships it does not name, the spec's sparse-fieldset exemption from full linkage covering the `included` members they linked.
- **Graph-derived include paths are typed to a depth of 2 hops** (`"comments.author"` works, `"comments.author.employer"` doesn't) — a TypeScript recursion-depth trade-off; `{ depth: 3 }` raises it one hop, and the runtime validation matches the same set. Declaring the surface explicitly with `Include.make` lifts the ceiling altogether (up to `Include.MAX_DEPTH`), because the derivation then recurses over the declaration rather than the graph.
- **Server-side `included` narrowing is not possible**: a handler's return type cannot depend on the runtime value of `?include=` (that's dependent typing). Client-side narrowing is provided via `Client.narrowIncluded`.
- **Relationship and identifier `meta` are untyped** (free-form records); resource and document meta are typed via options.
- **Mutually recursive resources** (A ↔ B) need one interface annotation per resource in the cycle — `Resource.make`'s return type is inferred, and two inferred types cannot reference each other. See [Mutually recursive resources](resources.md#mutually-recursive-resources) for the pattern; everything derived from the definitions is unaffected.
- **`narrowIncluded` over a heterogeneous response narrows by the whole union, not per primary resource**: pass the union of the response's resource definitions (a family's members, say) and each path resolves against every member that declares it, never crossing a member's `paginated` relationship. `included` is document-wide, so it narrows to everything any member reaches; which primary resource reached a given entry is not tracked.
- **Atomic operations requests are accepted with or without the `ext` media type parameter**: spec-compliant clients send `application/vnd.api+json;ext="https://jsonapi.org/ext/atomic"` (accepted once the middleware declares the extension), but the bare media type is not rejected. Responses always carry the parameter.
